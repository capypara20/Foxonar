# 議論の記録

Foxonar の言葉と動きについて、何を、なぜそう決めたかの記録です。

- 決まった言葉の意味は [用語集](glossary.ja.md) に書く。ここには、そう決めた理由と経緯を残す。
- まだ決まっていない「どうやるか」は [設計書](design.ja.md) に書く。
- 新しい言葉を足したいときや、用語集の言葉を変えたいときは、ここに論点を足して話し、決まってから用語集に書く。
- 論点の見出しには、決まったら「（決定）」を付ける。
- 日本語のみ。

## A. 「処理」を「ステップ」に変えるか（決定）

- 「処理」は日常語として頻繁に使うため、用語としての意味と区別できない。前回のメモでも「検知の処理が止まる」と一般的な意味で使っている。
- ふだん「処理」を一般的な意味で使うので、使い分けを注意力に頼ると、いずれ混ざる。用語の側を変えれば、「処理」は今までどおり一般的な意味で使える。
- 決定：「ステップ」に変える。英語名の step とも揃う。

## B. 「イベント」を 3 つに分けるか（決定）

- 前回のメモでは「イベント」が 3 つの意味で使われている。
  - OS から受け取るもの（「`Other` を無視している」）
  - トリガーの条件（「監視フォルダ・イベント・フィルタ」）
  - Foxonar が外へ流すもの（「結果をイベントとして流し」）
- 決定：OS イベント／変化／通知 に分け、「イベント」は単独で使わない。
- 上の層（変化）を単に「イベント」と呼ばない理由：コードでは notify の型名 `Event` が OS イベントを指す。ドキュメントで「イベント」を別の意味にすると、コードと食い違う。

## C. 取りこぼしを 2 つに分けるか（決定）

- 意図しないもの（OS イベントを受け取れなかった）と、意図したもの（決まりに従って捨てた）は、対策も通知のしかたも違う。
- 決定：「溢れ」と「無視」に分ける。

## D. トリガー 1 つが走らせるジョブは 1 つか、複数か（決定）

- 1 つに限る場合：同じ条件で独立したジョブを 2 つ走らせたいとき、条件が同じトリガーを 2 つ書くことになる。
- 複数を許す場合：同じパスに対するジョブの順番が「トリガーの定義順 → トリガーの中の並び順」の 2 段になる。
- 決定：複数を許す。
- ジョブごとに別々のランになる。あるジョブが失敗しても、ほかのジョブは走る。
- 同じパスに対して、1 つのトリガーの中のジョブは、依存を書かなければ並行に走る（論点 H）。依存はトリガーに書く（論点 M）。ジョブを分けて得られるのは、失敗の独立、使い回し、並行に走らせられること。
- 使い分け：前の結果に依存するもの（アップロードしてから削除する、など）は、1 つのジョブのステップとして並べる。依存しないもの（サムネイルを作る、バックアップを取る、など）は、別々のジョブにする。
- 注意：前のジョブがファイルを移動・削除すると、後のジョブは対象のファイルが無いので走れない。無視になるか失敗になるかは、ロジックの議論で決める。

## E. ランの対象は「ファイル」か「パス」か（決定）

- 削除ではファイルがもう無い。名前変更では 2 つのパス（変更前と変更後）にまたがる。
- 決定：「パス」にする。名前変更では変更後のパスを対象パスとし、変更前のパスは付随する情報として渡す。

## F. 「コマンド」と「プロセス実行」は何が違うか（決定）

- 前回のメモではステップの例として両方を挙げているが、違いが書かれていない。
- どちらもプロセスを起動する。違いは、コマンドの文字列を誰が解釈するか。
  - プロセス実行：プログラムと引数の配列を OS に渡す。誰も文字列を解釈しないので、配列の 1 要素がそのまま引数 1 つになる。
  - シェル経由：シェル（`sh`、`cmd`、`powershell`）を起動し、1 本の文字列を渡す。シェルが文字列を読んで空白で区切り、`|` `>` `;` `$` `*` などを特別扱いしてから、プログラムを起動する。
- シェル経由でできること：パイプ、リダイレクト、`&&` でのつなぎ、環境変数の展開、シェルの組み込みコマンド（cmd の `copy` や `del` など）。
- シェル経由の問題：
  1. ファイル名がコマンドとして実行される。対象パスを文字列に埋め込むと、`"{path}"` と引用しても防げない。たとえば `$(touch pwned).jpg` という名前のファイルがあると、sh では二重引用符の中でも `touch pwned` が実行される。監視フォルダに書き込める人なら誰でも、Foxonar の権限でコマンドを実行できることになる。
  2. 引用やエスケープの規則がシェルごとに違う（sh、cmd、PowerShell）。同じ設定を Linux と Windows で使い回せない。
  3. 失敗が見えにくい。sh の既定では、パイプの途中のコマンドが失敗しても、最後のコマンドが成功すれば成功扱いになる。
  4. 止めにくい。タイムアウトなどでシェルを止めても、シェルが起動した子プロセスが残ることがある。
- プロセス実行にも注意点はある。
  - ファイル名が `-` で始まると、プログラムがオプションとして読むことがある（`-rf.jpg` など）。対象パスを常に絶対パスで渡せば、`/` や `C:\` で始まるので起きない。
  - Windows で `.bat` や `.cmd` を起動すると、中で cmd が動く。Rust の標準ライブラリにも、これが原因の脆弱性があった（CVE-2024-24576。Rust 1.77.2 で修正）。
- 決定：シェルは使わない。外部のプログラムを動かすステップは「プロセス実行」だけにし、プログラムと引数を指定する。英語名は `exec`（`run` はランの英語名と重なる）。
- 取り下げた案：対象パスを環境変数（`FOX_PATH` など）でも渡す案。シェルの文字列に安全にパスを渡すためのものだったので、シェルをやめたことで不要になった。
- 残り：プログラムの指定のしかた（論点 I）、プレースホルダ（論点 J）、`.bat` と `.cmd` の扱い（論点 K）。

## G. 「検知」を使うか（決定）

- 「イベント検知」のように、「検知」は上の層（OS より上）の意味で自然に使う言葉なので、禁止するより意味を決めて使うほうがよい。
- 決定：「検知する」は変化にだけ使う（「変化を検知する」）。OS イベントには「受け取る」を使う。用語集の「言い方の決まり」の表を参照。

## H. 同じパスで、ジョブを同時に走らせるか（決定）

- 決定：走らせる。1 つのトリガーの中のジョブは、依存を書かなければ並行に走る。依存はトリガーに明示する（論点 M）。
- 経緯：はじめは同時に走らせない案だった。次に、ジョブの中のステップを並行にする案（論点 L）を考えた。最終的に、ジョブの中は常に逐次にし、並行はジョブの単位で表す形にした。
- この形にした理由：
  - ジョブの定義（ステップを順番に並べたもの）を変えずに済む。
  - 失敗の単位がジョブのままになる。A が失敗しても B は走る。
  - 1 つのランで同時に動くプロセスは常に 1 つなので、同時実行数（ランの数）でプロセスの数を抑えられる。
- 注意：同じ対象パスに対して、複数のジョブが同時に動く。片方が移動や削除をするなら、もう片方との順番を依存で書く必要がある。
- 前回までの実行のルールのうち、次の 2 つが変わる。
  - 「同じファイルは同時に走らせない」→ 同じパスで同時に動ける発火は 1 つだけ。発火の中では、ジョブは依存に従って並行に走る。
  - 「同じファイルに別ジョブ：定義順に 1 つずつ」→ 同じパスに複数のトリガーが合ったときは、トリガーの定義順に、発火を 1 つずつ実行する。
- アプリ内のロックや、実行中に届いた変化を無視する決まりは、ランではなく発火の単位で考える。

## I. プログラムの指定のしかた（決定）

- 要望：フルパスか、環境変数で指定したい。主に (a) の意味。
  - (a) プログラム名だけ書き、環境変数 PATH から探す（`magick` と書けば PATH 上の `magick.exe` を使う）
  - (b) パスの中に環境変数を書く（`${env:LOCALAPPDATA}\Programs\tool.exe`）
- 決定：両方使えるようにする。
- (a) の注意：常駐プロセスの PATH は、ターミナルの PATH と違うことがある（Windows のサービスや systemd から起動した場合など）。「ターミナルでは動くのに、常駐させると動かない」が起きやすい。
- 残り（設計書）：プログラムを確かめるタイミング。

## J. プレースホルダ（用語は決定）

- 要望：変化を検知したファイルの名前などの可変値は、Foxonar の中でだけ意味を持つ名前で扱いたい。
- 用語（決定）：「変数」ではなく「プレースホルダ」と呼ぶ。設定ファイルの上でだけ使う言葉なので、ソースコードの話とはぶつからない。
- 残り（設計書）：書き方、使えるプレースホルダの一覧、安全のための決まり。

## K. `.bat` と `.cmd` を許すか（決定）

- 決定：許す。PowerShell のスクリプト（`.ps1`）も使える。
- 仕組みの注意：
  - Windows は `.bat` と `.cmd` を直接は実行できず、内部で cmd を起動して渡す。このとき cmd が引数を読み直すので、仕組みとしてはシェルを通すのと同じになる。
  - Rust 1.77.2 以降の標準ライブラリは、`.bat` と `.cmd` に渡す引数を cmd 向けにエスケープし、安全にエスケープできない引数があるとエラーを返す（CVE-2024-24576 の修正）。Foxonar では、そのステップの失敗になる。変わった名前のファイルで失敗することはあっても、意図しないコマンドが実行されることはない。
  - 禁止すると、バッチを使いたい人は `cmd /C ...` と書くことになる。こちらは Rust のこの保護の対象外なので、かえって危ない。
  - `.ps1` は直接実行できないので、プログラムに `powershell`（または `pwsh`）を指定し、引数を `-File スクリプト ${path}` とする。`-File` のあとの引数は、スクリプトのパラメータとしてそのまま渡る。実行ポリシー（ExecutionPolicy）の設定で止まることがあるので、必要なら `-ExecutionPolicy` で指定する。
  - Linux のシェルスクリプトは、先頭に `#!` があれば OS が直接実行する。引数は読み直されないので、`.bat` のような注意は要らない（スクリプトの中で `"$1"` と引用する必要はある）。

## L. ジョブの中のステップを並行に走らせるか（決定）

- 決定：走らせない。ジョブの中は常に逐次。並行にしたいものは別々のジョブにし、論点 H のとおりトリガーの中で並行に走らせる。
- 検討した表現（ジョブ単位の切り替え、ステップのグループ、ステップごとの依存）は、どれもジョブの定義を複雑にするので採らなかった。

## M. ジョブ同士の依存の書き方（決定）

- 依存はジョブではなくトリガーに書く。同じジョブを別のトリガーで使い回すと、一緒に走るジョブが変わるため。GitHub Actions はジョブに `needs` を書くが、ジョブを使い回さないのでそれで足りる。
- 決定：依存を書かなければ並行に走る（GitHub Actions と同じ。論点 H）。以前の「定義順に 1 つずつ」はやめる。
  - 決定：組み込みの移動や削除のステップを持つジョブが、ほかのジョブと依存なしで並行になっている場合は、設定の読み込み時に警告する。プロセス実行が何をするかは Foxonar には分からないので、対象は組み込みのステップだけ。
- 決定：依存先のジョブが失敗したら、後のジョブは始めない（無視。理由は「依存先の失敗」として通知する）。GitHub Actions の `needs` の既定と同じ。
- 決定：1 つのジョブは、複数のジョブに依存できる（合流）。並行に走ったジョブの両方を待ってから始める、という形になる（例：アップロードとバックアップが両方済んでから、元ファイルを消す）。
  - 合流のときの条件は「依存先がすべて成功したら」だけにする。「どれか 1 つが成功したら」「全部終わったら（成否は問わない）」は、使う場面がはっきりしてから足す。
  - 依存先が 1 つの場合や、1 列につながる場合（A → B → C）は、条件を考える必要はない。依存先が失敗したら始めない、だけで決まる。

## N. 同じジョブを、同時にいくつも走らせるか（決定）

- きっかけ：同時実行数が「ジョブごとの上限（既定 1）」のままだと、ファイル X と Y が同時に届いたとき、Y のランは X の同じジョブが終わるまで待つ。別のパスなので、ふつうは待つ必要が無い。
- 考え方：トリガーに合ったら、すぐ発火してジョブが走る（論点 H）。同時実行数はこの流れを変えるものではなく、混んでいるときだけ効くブレーキとする。
- 同じジョブが同時にいくつも動くのは、次のとき。
  - 複数のトリガーが、同じジョブを使い回している
  - 同じトリガーに、複数のパスの変化が合った
- ジョブの中身によっては、同時に 2 つ動くと壊れる（例：同じ `一覧.csv` に追記する、同時に 1 つしか起動できないプログラムを使う、届いた順に連番を振る）。壊れるかどうかは、ジョブの中身を知っている利用者にしか分からない。
- 決定：
  - ジョブごとの上限は、ジョブを定義するときに書く。既定の値は用語集では決めない。
  - 全体の上限は残す。一度に大量のファイルが届いたとき（まとめてコピー、zip の展開、クラウドの最初の同期など）に、PC を守るため。
  - 上限に引っかかったランは、待ってから走る。無視はしない。
- 残り（設計書）：ジョブごとの上限を書かなかったときの扱い、全体の上限の値の決め方。
