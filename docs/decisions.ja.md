# 議論の記録

Foxonar の言葉と動きについて、何を、なぜそう決めたかの記録です。

- 決まった言葉の意味は [用語集](glossary.ja.md) に書く。ここには、そう決めた理由と経緯を残す。
- 決まった「どうやるか」は [設計書](design.ja.md) に、まだ決めていないことは [宿題一覧](todo.ja.md) に書く。
- 新しい言葉を足したいときや、用語集の言葉を変えたいときは、ここに論点を足して話し、決まってから用語集に書く。
- 論点の見出しには、決まったら「（決定）」を付ける。
- 日本語のみ。

## A. 「処理」を「ステップ」に変えるか（決定）

- 「処理」は日常語として頻繁に使うため、用語としての意味と区別できない。前回のメモでも「検知の処理が止まる」と一般的な意味で使っている。
- ふだん「処理」を一般的な意味で使うので、使い分けを注意力に頼ると、いずれ混ざる。用語の側を変えれば、「処理」は今までどおり一般的な意味で使える。
- 決定：「ステップ」に変える。英語名の step とも揃う。

## B. 「イベント」を 3 つに分けるか（決定）

- 前回のメモでは「イベント」が 3 つの意味で使われている。
  - OS から受け取るもの（「`Other` を無視している」）
  - トリガーの条件（「監視フォルダ・イベント・フィルタ」）
  - Foxonar が外へ流すもの（「結果をイベントとして流し」）
- 決定：OS イベント／変化／通知 に分け、「イベント」は単独で使わない。
- 上の層（変化）を単に「イベント」と呼ばない理由：コードでは notify の型名 `Event` が OS イベントを指す。ドキュメントで「イベント」を別の意味にすると、コードと食い違う。

## C. 取りこぼしを 2 つに分けるか（決定）

- 意図しないもの（OS イベントを受け取れなかった）と、意図したもの（決まりに従って捨てた）は、対策も通知のしかたも違う。
- 決定：「溢れ」と「無視」に分ける。

## D. トリガー 1 つが走らせるジョブは 1 つか、複数か（決定）

- 1 つに限る場合：同じ条件で独立したジョブを 2 つ走らせたいとき、条件が同じトリガーを 2 つ書くことになる。
- 複数を許す場合：同じパスに対するジョブの順番が「トリガーの定義順 → トリガーの中の並び順」の 2 段になる。
- 決定：複数を許す。
- ジョブごとに別々のランになる。あるジョブが失敗しても、ほかのジョブは走る（あとで訂正：論点 M で依存を足したので、正しくは「依存していないほかのジョブは走る」）。
- 同じパスに対して、1 つのトリガーの中のジョブは、依存を書かなければ並行に走る（論点 H）。依存はトリガーに書く（論点 M）。ジョブを分けて得られるのは、失敗の独立、使い回し、並行に走らせられること。
- 使い分け：前の結果に依存するもの（アップロードしてから削除する、など）は、1 つのジョブのステップとして並べる。依存しないもの（サムネイルを作る、バックアップを取る、など）は、別々のジョブにする。
- 注意：前のジョブがファイルを移動・削除すると、後のジョブは対象パスにファイルが無いので走れない。無視になるか失敗になるかは、ロジックの議論で決める。
  - 決定（あとで追記）：無視にする。削除以外の変化で発火したランは、始める直前に対象パスがあるかを確かめ、無ければ無視にする。削除で発火したランは確かめない（設計書 6 章）。
  - 決定（あとで追記）：依存先があるランは確かめない（論点 M）。

## E. ランの対象は「ファイル」か「パス」か（決定）

- 削除ではファイルがもう無い。名前変更では 2 つのパス（変更前と変更後）にまたがる。
- 決定：「パス」にする。名前変更では変更後のパスを対象パスとし、変更前のパスは付随する情報として渡す。

## F. 「コマンド」と「プロセス実行」は何が違うか（決定）

- 前回のメモではステップの例として両方を挙げているが、違いが書かれていない。
- どちらもプロセスを起動する。違いは、コマンドの文字列を誰が解釈するか。
  - プロセス実行：プログラムと引数の配列を OS に渡す。誰も文字列を解釈しないので、配列の 1 要素がそのまま引数 1 つになる。
  - シェル経由：シェル（`sh`、`cmd`、`powershell`）を起動し、1 本の文字列を渡す。シェルが文字列を読んで空白で区切り、`|` `>` `;` `$` `*` などを特別扱いしてから、プログラムを起動する。
- シェル経由でできること：パイプ、リダイレクト、`&&` でのつなぎ、環境変数の展開、シェルの組み込みコマンド（cmd の `copy` や `del` など）。
- シェル経由の問題：
  1. ファイル名がコマンドとして実行される。対象パスを文字列に埋め込むと、`"{path}"` と引用しても防げない。たとえば `$(touch pwned).jpg` という名前のファイルがあると、sh では二重引用符の中でも `touch pwned` が実行される。監視フォルダに書き込める人なら誰でも、Foxonar の権限でコマンドを実行できることになる。
  2. 引用やエスケープの規則がシェルごとに違う（sh、cmd、PowerShell）。同じ設定を Linux と Windows で使い回せない。
  3. 失敗が見えにくい。sh の既定では、パイプの途中のコマンドが失敗しても、最後のコマンドが成功すれば成功扱いになる。
  4. 止めにくい。タイムアウトなどでシェルを止めても、シェルが起動した子プロセスが残ることがある。
- プロセス実行にも注意点はある。
  - ファイル名が `-` で始まると、プログラムがオプションとして読むことがある（`-rf.jpg` など）。対象パスを常に絶対パスで渡せば、`/` や `C:\` で始まるので起きない。
  - Windows で `.bat` や `.cmd` を起動すると、中で cmd が動く。Rust の標準ライブラリにも、これが原因の脆弱性があった（CVE-2024-24576。Rust 1.77.2 で修正）。
- 決定：シェルは使わない。外部のプログラムを動かすステップは「プロセス実行」だけにし、プログラムと引数を指定する。英語名は `exec`（`run` はランの英語名と重なる）。
- 取り下げた案：対象パスを環境変数（`FOX_PATH` など）でも渡す案。シェルの文字列に安全にパスを渡すためのものだったので、シェルをやめたことで不要になった。
- 残り：プログラムの指定のしかた（論点 I）、プレースホルダ（論点 J）、`.bat` と `.cmd` の扱い（論点 K）。

## G. 「検知」を使うか（決定）

- 「イベント検知」のように、「検知」は上の層（OS より上）の意味で自然に使う言葉なので、禁止するより意味を決めて使うほうがよい。
- 決定：「検知する」は変化にだけ使う（「変化を検知する」）。OS イベントには「受け取る」を使う。用語集の「言い方の決まり」の表を参照。

## H. 同じパスで、ジョブを同時に走らせるか（決定）

- 決定：走らせる。1 つのトリガーの中のジョブは、依存を書かなければ並行に走る。依存はトリガーに明示する（論点 M）。
- 経緯：はじめは同時に走らせない案だった。次に、ジョブの中のステップを並行にする案（論点 L）を考えた。最終的に、ジョブの中は常に逐次にし、並行はジョブの単位で表す形にした。
- この形にした理由：
  - ジョブの定義（ステップを順番に並べたもの）を変えずに済む。
  - 失敗の単位がジョブのままになる。B が A に依存していなければ、A が失敗しても B は走る。
  - 1 つのランで同時に動くプロセスは常に 1 つなので、同時実行数（ランの数）でプロセスの数を抑えられる。
- 注意：同じ対象パスに対して、複数のジョブが同時に動く。片方が移動や削除をするなら、もう片方との順番を依存で書く必要がある。
- 前回までの実行の決まりのうち、次の 2 つが変わる。
  - 「同じファイルは同時に走らせない」→ 同じパスで同時に動ける発火は 1 つだけ。発火の中では、ジョブは依存に従って並行に走る。
  - 「同じファイルに別ジョブ：定義順に 1 つずつ」→ 同じパスに複数のトリガーが合ったときは、トリガーの定義順に、発火を 1 つずつ実行する。
- アプリ内のロックや、実行中に届いた変化を無視する決まりは、ランではなく発火の単位で考える。
  - あとで変更：発火中に届いた変化は、無視せずに待ち表で待たせ、今の発火が終わってから発火することにした（論点 V）。

## I. プログラムの指定のしかた（決定）

- 要望：フルパスか、環境変数で指定したい。主に (a) の意味。
  - (a) プログラム名だけ書き、環境変数 PATH から探す（`magick` と書けば PATH 上の `magick.exe` を使う）
  - (b) パスの中に環境変数を書く（`${env:LOCALAPPDATA}\Programs\tool.exe`）
- 決定：両方使えるようにする。
- (a) の注意：常駐プロセスの PATH は、ターミナルの PATH と違うことがある（Windows のサービスや systemd から起動した場合など）。「ターミナルでは動くのに、常駐させると動かない」が起きやすい。
- 残り（宿題一覧）：プログラムを確かめるタイミング。

## J. プレースホルダ（用語は決定）

- 要望：変化を検知したファイルの名前などの可変値は、Foxonar の中でだけ意味を持つ名前で扱いたい。
- 用語（決定）：「変数」ではなく「プレースホルダ」と呼ぶ。設定ファイルの上でだけ使う言葉なので、ソースコードの話とはぶつからない。
- 残り（宿題一覧）：書き方、使えるプレースホルダの一覧、安全のための決まり。

## K. `.bat` と `.cmd` を許すか（決定）

- 決定：許す。PowerShell のスクリプト（`.ps1`）も使える。
- 仕組みの注意：
  - Windows は `.bat` と `.cmd` を直接は実行できず、内部で cmd を起動して渡す。このとき cmd が引数を読み直すので、仕組みとしてはシェルを通すのと同じになる。
  - Rust 1.77.2 以降の標準ライブラリは、`.bat` と `.cmd` に渡す引数を cmd 向けにエスケープし、安全にエスケープできない引数があるとエラーを返す（CVE-2024-24576 の修正）。Foxonar では、そのステップの失敗になる。変わった名前のファイルで失敗することはあっても、意図しないコマンドが実行されることはない。
  - 禁止すると、バッチを使いたい人は `cmd /C ...` と書くことになる。こちらは Rust のこの保護の対象外なので、かえって危ない。
  - `.ps1` は直接実行できないので、プログラムに `powershell`（または `pwsh`）を指定し、引数を `-File スクリプト ${path}` とする。`-File` のあとの引数は、スクリプトのパラメータとしてそのまま渡る。実行ポリシー（ExecutionPolicy）の設定で止まることがあるので、必要なら `-ExecutionPolicy` で指定する。
  - Linux のシェルスクリプトは、先頭に `#!` があれば OS が直接実行する。引数は読み直されないので、`.bat` のような注意は要らない（スクリプトの中で `"$1"` と引用する必要はある）。

## L. ジョブの中のステップを並行に走らせるか（決定）

- 決定：走らせない。ジョブの中は常に逐次。並行にしたいものは別々のジョブにし、論点 H のとおりトリガーの中で並行に走らせる。
- 検討した表現（ジョブ単位の切り替え、ステップのグループ、ステップごとの依存）は、どれもジョブの定義を複雑にするので採らなかった。

## M. ジョブ同士の依存の書き方（決定）

- 依存はジョブではなくトリガーに書く。同じジョブを別のトリガーで使い回すと、一緒に走るジョブが変わるため。GitHub Actions はジョブに `needs` を書くが、ジョブを使い回さないのでそれで足りる。
- 決定：依存を書かなければ並行に走る（GitHub Actions と同じ。論点 H）。以前の「定義順に 1 つずつ」はやめる。
  - 決定：組み込みの移動や削除のステップを持つジョブが、ほかのジョブと依存なしで並行になっている場合は、設定の読み込み時に警告する。プロセス実行が何をするかは Foxonar には分からないので、対象は組み込みのステップだけ。
- 決定：依存先のジョブが失敗したら、後のジョブは始めない（無視。理由「依存先の失敗」を添えて、通知として流す。あとで訂正：理由は「依存先が成功しなかった」に揃えた）。GitHub Actions の `needs` の既定と同じ。
  - 決定（あとで追記）：依存先のランが無視になったときも、後のジョブは始めない。「成功してから始める」なので、失敗でも無視でも、成功しなかったら始めない。理由は「依存先が成功しなかった」とする（設計書 6 章）。
  - 決定（あとで追記）：依存先があるランは、依存先がすべて成功したら、対象パスを確かめずに始める。始める直前に対象パスを確かめるのは、依存先の無いランだけにする（論点 D）。
    - 例：ジョブ A が対象パスのファイルを `done\` へ移動し、A に依存するジョブ B が Slack に知らせる。確かめると、B のランは対象パスが無いので無視になってしまう（Roze：A が成功しているなら、B は始まるはず）。
    - B に渡る `${path}` などは、移動の前のパスのまま。B がファイルを開こうとするステップなら、そこで失敗になる。
- 決定：1 つのジョブは、複数のジョブに依存できる（合流）。並行に走ったジョブの両方を待ってから始める、という形になる（例：アップロードとバックアップが両方済んでから、元ファイルを消す）。
  - 合流のときの条件は「依存先がすべて成功したら」だけにする。「どれか 1 つが成功したら」「全部終わったら（成否は問わない）」は、使う場面がはっきりしてから足す。
  - 依存先が 1 つの場合や、1 列につながる場合（A → B → C）は、条件を考える必要はない。依存先が失敗したら始めない、だけで決まる。

## N. 同じジョブを、同時にいくつも走らせるか（決定）

- きっかけ：同時実行数が「ジョブごとの上限（既定 1）」のままだと、ファイル X と Y が同時に届いたとき、Y のランは X の同じジョブが終わるまで待つ。別のパスなので、ふつうは待つ必要が無い。
- 考え方：トリガーに合ったら、すぐ発火してジョブが走る（論点 H）。同時実行数はこの流れを変えるものではなく、混んでいるときだけ効くブレーキとする。
- 同じジョブが同時にいくつも動くのは、次のとき。
  - 複数のトリガーが、同じジョブを使い回している
  - 同じトリガーに、複数のパスの変化が合った
- ジョブの中身によっては、同時に 2 つ動くと壊れる（例：同じ `一覧.csv` に追記する、同時に 1 つしか起動できないプログラムを使う、届いた順に連番を振る）。壊れるかどうかは、ジョブの中身を知っている利用者にしか分からない。
- 決定：
  - ジョブごとの上限は、ジョブを定義するときに書く。既定の値は用語集では決めない。
  - 全体の上限は残す。一度に大量のファイルが届いたとき（まとめてコピー、zip の展開、クラウドの最初の同期など）に、PC を守るため。
  - 上限に引っかかったランは、待ってから走る。無視はしない。
- 残り（宿題一覧）：ジョブごとの上限を書かなかったときの扱い、全体の上限の値の決め方。

## O. 常駐する部分と画面を分けるか（決定）

- Foxonar は、常駐して監視とランを行う部分と、設定やログを見る部分でできている。
- 画面の作り方として、ネイティブ GUI（egui など）と、Web の画面（Web サーバを内蔵する）を比べた。
  - ネイティブ GUI：Rust だけで作れる。ポートを開けないので安全側。ただし、画面のない Linux では動かず、ほかの PC やスマホからも使えない。
  - Web：見た目を豊かにでき、画面のないサーバーやほかの PC からも使える。ただし、Web サーバを守る工夫が要る。
- 要望：画面のないサーバーでも使いたい。ほかの PC やスマホから見るのも、いつかは欲しい。
- 決定：常駐する部分を「コア」と呼び、画面を持たせない。Web UI を閉じていても、コアは監視とランを続ける。
- 決定：設定やログを見る画面は、コアの中の Web サーバが出す「Web UI」にする。ターミナルから操作するコマンドは「CLI」と呼ぶ。
- 「画面」は用語にしない。ターミナルの画面にも Web の画面にも取れるため。
- Web サーバの守り方：
  - 既定では、その PC からの接続（127.0.0.1）だけを受け付ける。
  - 決定：合言葉（トークン）は、同じ PC からの接続でも SSH のトンネルでも、いつでも必要にする。HTTP を許す場面でも省かない。1 台の PC をほかのユーザーも使っていると、その人も 127.0.0.1 に接続できるため。
  - Web UI から設定を変えられる＝プログラムを実行させられる、ということなので、守りは必須。ブラウザで開いた別のサイトから localhost に要求を送る攻撃（CSRF、DNS リバインディング）があるので、「localhost だけで待ち受ける」だけでは足りない。
  - 画面のないサーバーでは、SSH のトンネル（`ssh -L`）を使って手元のブラウザから開く。
  - ほかの PC やスマホからの接続は、あとで足す。
- 英語名：core、web ui、cli。`core` は Rust に最初からある `core` と名前がぶつかるので、コードではクレート名を `foxonar-core` にするなどして避ける。
- HTTPS の扱い：
  - 要望：HTTPS を強制したい。
  - 自分で作った証明書（自己署名）だと、ブラウザが警告を出す。公開の認証局は、`localhost` や `127.0.0.1` 向けの証明書を出さない。
  - 同じ PC の中の接続は PC の外に出ない。SSH のトンネルは、すでに SSH で暗号化されている。どちらも HTTPS にしても守りはほとんど増えず、警告の手間だけが増える。localhost の危険（CSRF、DNS リバインディング）は、HTTPS ではなく合言葉などで防ぐ。
  - 決定：ほかの PC やスマホからの接続は、HTTPS を強制する。同じ PC からの接続と SSH のトンネルでは、HTTP も許す。
  - コアから見ると、同じ PC からの接続も SSH のトンネルも、どちらも `127.0.0.1` からの接続になる。つまり「`127.0.0.1` で待ち受けるときは HTTP も許し、それ以外のアドレスで待ち受けるときは HTTPS だけにする」という決まりと同じになる。
- 残り（宿題一覧）：Web UI の作り方、ポート、合言葉の方式、証明書の用意のしかた（自分で作る、Tailscale を使う、など）。

## P. コアをどう起動するか（決定）

- 起動のしかたは 2 つある。
  - ログイン時に、ユーザーとして起動する（Windows のスタートアップやタスク スケジューラ、Linux の `systemctl --user` など）。
  - OS のサービスとして起動する（Windows のサービス、Linux の systemd）。ログインしなくても動く。
- サービスの注意：
  - Windows のサービスは「セッション 0」という別の場所で動くので、画面もデスクトップ通知も出せない。Linux のシステムのサービスも、デスクトップ通知を出しにくい。
  - Windows のサービスは、既定では強い権限（LocalSystem）で動く。プロセス実行のステップも、その権限で走る。
  - ドライブ文字（`Z:` など）の割り当ては、ログインごとのものなので、サービスからは見えない。ネットワーク上の共有フォルダは `\\server\share` のような UNC パスで書く必要がある。
- 決定：両方を選べるようにする。サーバーとして動かすときはサービス、デスクトップで使うときはログイン時の起動、と使い分ける。
- 決定：サービスでも、動かすユーザーを決められるようにする。権限が強すぎる問題を避けるため。また、そのユーザーの権限で共有フォルダに届くようにするため。
- 残り（宿題一覧）：サービスへの登録のしかた（Windows、systemd）。

## Q. ログをどう分けるか（決定）

- 要望：
  - ジョブが無くても、そのフォルダにどんなファイルが来たかを確かめたい。
  - ログファイルは、困ったときにならないと読まない。Web UI で見たい。
- 「履歴」「処理履歴」は用語にしない。「処理」は論点 A で用語にしないと決めているため。記録はすべて「ログ」と呼び、何の記録かで分ける。
- 決定：ログを 3 つに分ける。
  - 検知ログ：検知した変化 1 件ごとの記録。作成・変更・削除・名前変更のすべてを残す。トリガーに合わなかった変化も残す。OS イベントではなく変化を残すので、ファイル 1 つのコピーで出る行は少ない（あとで訂正：はじめは「何行も出ることはない」と書いたが、デバウンス時間より長くかかるコピーでは、複数の変化になることがある）。
  - ランログ：ラン 1 回分ごとの記録。
  - アプリログ：Foxonar 自身の動き（起動、停止、設定の読み込み、エラーなど）の記録。
- 「システムログ」とは呼ばない。OS のログ（Windows のイベントログ、Linux の journald）と紛れるため。
- 決定：検知ログとランログは、ID でつなぐ。
  - 検知ログの 1 行（検知した変化 1 件）ごとに「検知 ID」、ラン 1 回分ごとに「ラン ID」を付ける。1 件ずつに付く、重ならない番号。ログの名前と揃えて「検知 ID」と呼ぶ（「変化 ID」とは呼ばない）。
  - ランログには、そのランのもとになった変化の検知 ID を書く。検知ログには、発火やランのことは書かない。
  - Web UI では、ランログの行から「もとの変化」を、検知ログの行から「この変化で走ったラン」を、たどって見せる。
- 決定：ランログには、ラン ID、検知 ID、トリガー ID、ジョブ ID を書く。
  - ジョブ ID だけでは、1 行ずつを見分けられない。同じジョブが、別のパスについて何度も走るため。ラン ID は、その行だけの番号として要る。
  - トリガー ID も要る。ジョブを複数のトリガーから使い回すと、同じ変化・同じジョブのランが、別々のトリガーから走ることがあるため。
  - トリガー ID とジョブ ID は、設定ファイルの中のトリガーとジョブを指す。ジョブを指す ID は、トリガーや依存を書くためにもともと設定に要るので、ジョブの一覧を別に作る必要はない。
- 決定：ランログには、そのときのジョブの名前も書く。あとでジョブの名前を変えたり消したりしても、古いランログが読めるようにするため。
- ID は 2 種類ある。検知 ID とラン ID は、実行時にコアが振る。トリガー ID とジョブ ID は、設定に書く（あとで追記：論点 U で監視フォルダ ID も足した。これも設定に書く）。
- 英語名：detection log、run log、app log。検知ログを change log と訳すと、ソフトの更新履歴（CHANGELOG）と紛れるため。
- 残り：変化の段階の無視（発火中に同じパスの変化が届いた、など）をどこに残すか（あとで訂正：発火中に届いた変化は無視しないことにした。変化の段階の無視の例は、自分が起こした変化など。論点 V）。溢れをどこに残すか（案：検知ログに「抜けがあった」ことを残す。検知ログで来たファイルを確かめるなら、抜けがあったことも分からないと困るため）。
  - 決定（あとで追記）：変化の段階の無視（自分が起こした変化、作成のあと削除された）は、ランログに、走るはずだったジョブごとに「無視」の行を書く。依存先や対象パスの無視と同じ場所なので、「なぜジョブが走らなかったか」は全部ランログで分かる。溢れは、検知ログに「ここで抜けがあった」行を 1 行残し、アプリログにも書く。検知ログで来たファイルを確かめるとき、抜けにも気づけるようにするため（設計書 7 章。2026-10-20）。
- 決定（あとで追記、2026-10-20）：待ち表でまとめ直したら合わなくなったとき、待っている間に設定を読み直したらトリガーが消えた・合わなくなったときも、無視として、ランログに、走るはずだったジョブごとに「無視」の行を書く（設計書 5.9、4.2、7.2）。
  - 理由：書かないと、「なぜジョブが走らなかったか」が、ランログだけでは分からない。「作成のあと削除された」も、まとめ直したら合わなくなったものの一種なので、書くほうが揃う。めったに起きないので、ログの量はほとんど増えない。
- 決定（あとで追記、2026-10-20）：ランログの行は、ランを始めたときではなく、発火したときに書く（あとで変更。前は「始めたときに書く」だった）。同時実行数の上限や依存先を待っている間は、結果を「待っている」にする（設計書 2.5、7.2）。
  - 理由：発火したがまだ始まっていないランを、コアが落ちても残すため（設計書 2.5）。ランログとは別の所に書く案もあったが、ランログに書けば、Web UI で待っているランも見える。
  - 注意：「待っている」は、待ち表（発火の前に、パスが待つ所）とは別のもの。ランログの「待っている」は、発火したあと、始まるのを待っている。
- 残り：トリガーの名前も、ジョブの名前と同じように残すか。
  - 決定（あとで追記、2026-10-20）：トリガーにも名前を付け、ランログに、そのときのトリガーの名前も書く。ジョブの名前と同じ理由（設計書 4.3、7.2）。
- 決定（あとで追記、2026-10-20）：プロセス実行の出力は、成功したランでは残さない。成功しなかったとき（失敗・中断）は、標準エラーを残し、標準出力は最後の数行だけを残す。ランログの「理由・エラーの中身」は、標準エラーの最後の数行、空なら標準出力の最後の数行（設計書 7.1、7.2）。
  - Roze の案：標準出力は要らない。標準エラーだけあれば、エラーのときに嬉しい。成功したときは、成功したと分かれば足りる。
  - 標準出力の最後の数行も残す理由：robocopy は、エラーも標準出力に出す（標準エラーには何も出さない）。bat の `echo` や Python の `print` でエラーを書くスクリプトも同じ。標準エラーだけだと、失敗の理由が残らない。
- 決定（あとで追記、2026-10-20）：検知ログに「見つけ方」の列を足す。再スキャンで見つけた変化にだけ「再スキャン（起動したとき）」などと書く（設計書 7.2）。
  - 理由：日時は見つけた時刻なので、起動したときの再スキャンでは、夜の間に置かれたファイルも朝の時刻で残る。2026-10-20、grill で決まったことを組み合わせて試したときに見つけた。
- 決定（あとで追記、2026-10-20）：どの版の設定で走ったかは、ランログに書かない。設定を読み直したことは、時刻とともにアプリログに書く。版の番号は付けない（Roze：設定ファイルの版を書かなくてよいが、設定を読み直したことはログに欲しい）。設計書 4.2、7.2。
- 残り（宿題一覧）：保存期間、ID の付け方（検知 ID とラン ID の振り方、トリガー ID とジョブ ID を利用者がつけるか自動で振るか）、プロセス実行の出力（標準出力・標準エラー）の扱い。
  - 決定（あとで追記）：プロセス実行の大きな出力は、ラン 1 回ごとのファイルに残し、ランログからたどれるようにする（設計書 7 章）。どれくらいの大きさまで残すかは、まだ決めること。

## R. デスクトップ通知（決定）

- 要望：監視フォルダが 1 つで、ファイルがたまにしか来ない場合に、来たことを OS の通知（Windows の右下に出るトースト通知など）で知らせてほしい。
- 決定：これを「デスクトップ通知」と呼ぶ。Windows では「トースト通知」と呼ぶが、Linux やブラウザでは「デスクトップ通知」と呼ぶのが普通で、OS をまたいで使えるため。
- 用語集の「通知」（Foxonar の中の記録）とは別物。デスクトップ通知は、通知を購読するものの 1 つ。動詞も分け、通知は「流す」、デスクトップ通知は「出す」と言う。
- 決定：何を知らせるか（発火したとき、成功したとき、失敗したとき、など）は利用者が選ぶ。「失敗だけ」を既定にする案は、上の要望に合わないので採らなかった。
- 注意：Windows のサービスと画面のないサーバーでは、デスクトップ通知を出せない（論点 P）。
- 英語名：desktop notification。通知（notice）とは英語でも別の言葉になる。
- 残り（宿題一覧）：どこに書くか（トリガーか、ジョブか）、一度にたくさん届いたときのまとめ方、サーバーでの代わり（Webhook、メールなど）。
- 決定（あとで追記、2026-10-20）：選べるのは、変化を検知したとき（監視フォルダに書く。ジョブが無くても使える。上の要望のため）、ランが成功したとき、ランが失敗したとき（中断も含む）の 3 つ。Foxonar 自身の困りごと（溢れ、設定の読み込みの失敗、書き込みが終わらない）は、デスクトップ通知の選択肢にしない（Roze が選ばなかった）。アプリログと Web UI で知らせる（設計書 8）。
- 決定（あとで追記、2026-10-20）：一度にたくさん届いたときは、最初の 1 つはすぐ出し、続けて届いたものは、落ち着いてから 1 つにまとめる（例：写真 500 枚 →「cat.jpg が来ました」「ほか 499 個が来ました」）。ファイルがたまにしか来ない場合は、待たずにすぐ知らせたいため（設計書 8）。

## S. 設定ファイルを誰が書くか（決定）

- 決定：設定は Web UI から書くのを基本にする。ただし、人が設定ファイルを直接編集してもよい。
- そのため、設定ファイルは人が読める形にする。
- 注意：
  - Web UI で開いている間に、人がファイルを直接書き換えることがある。Web UI が古い内容のまま保存すると、人の書き換えが消える。
  - Web UI から保存すると、人が書いたコメントや並び順が消えることがある。
- 残り（宿題一覧）：ファイルの形式、書き込みのしかた（一時ファイルに書いてから名前を変える、など）、読み込みに失敗したときの扱い（案：前の設定のまま動き続ける）、直接の編集に気づく方法（案：コアが設定ファイルの書き換えに気づいて読み直す）、上の 2 つの注意への対策。
  - 決定（あとで追記）：形式は TOML にする。設定ファイルが書き換わったことにコアが気づき、自動で読み直す（設計書 4 章）。
  - 決定（あとで追記）：待ち表で待っている間に設定を読み直したら、発火するとき（待ち表を出るとき）の設定を使う。トリガーが消えていれば発火しない（論点 V、設計書 4 章）。
  - 決定（あとで追記、2026-10-20）：動いている間に読み直して失敗したら、前の設定のまま動き続け、アプリログと Web UI で知らせる。起動したときに失敗したら、起動しない（Roze。おすすめは「最後に正しく読めた設定で動く」だったが、起動しないほうを選んだ）。設計書 4.2。
  - 決定（あとで追記、2026-10-20）：上の 1 つめの注意への対策。Web UI から保存する前に、開いたあとに設定ファイルが書き換わっていないかを確かめ、書き換わっていたら保存せずに知らせる（設計書 4.1）。2 つめの注意（コメントと並び順）は、宿題一覧 4.1 の「コメントと並び順」のまま。

## T. 監視フォルダで、検知するものを絞るか（決定）

- 要望：すべての変化を検知ログに残すと、量が増える（Office の一時ファイル `~$…`、ダウンロード中の `.crdownload` や `.part` など）。Cat-watcher と同じように、絞り込みの機能で対応したい。
- 決定：監視フォルダごとに、検知するものを絞れるようにする。絞る条件の例：
  - 隠しファイルを含むか
  - ファイルとフォルダのどちらの変化を検知するか
  - 名前やパターン
- 決定：トリガーの無い監視フォルダを許す。ジョブは無くても、検知ログを残したい場合があるため。
- 決定（あとで追記）：監視フォルダの条件の外から中への名前変更は作成、中から外への名前変更は削除として扱う。外から入ってきた移動を作成とするのと同じ考え方（設計書 5 章）。
  - 例：`*.crdownload` を外している監視フォルダで、`photo.jpg.crdownload` が `photo.jpg` になると、`photo.jpg` の作成になる。
- 注意：
  - 絞り込みは 2 か所に出てくる。監視フォルダの条件で外れたものは、検知しない（検知ログにも残らない）。トリガーのフィルタで外れたものは、検知はする（検知ログに残る）が、発火しない。
  - 「隠しファイル」の意味は OS で違う。Windows ではファイルの属性（隠し属性）、Linux では名前が `.` で始まるもの。
- 決定（あとで追記、2026-10-20）：監視フォルダの条件で外れたフォルダは、その中のパスも、見る深さの末端まですべて外す。フォルダが入ってきたときも、条件を先に当て、外れたフォルダの中は再スキャンしない（設計書 5.1）。
  - 理由：名前が `.git` のものを外すと書いたら、`.git` という名前のフォルダが来たとき、その下の末端まで、ファイルもフォルダも全部外すと思う（Roze）。`.gitignore` と同じ考え方。
  - 例：`.git\index`（commit のたびに書き換わる）や `.git\objects\` の中は、名前が `.git` ではないが、検知しない。
- 決定（あとで追記、2026-10-20）：隠しファイルを含まない監視フォルダでは、隠しファイルの削除も検知しない（Roze：条件が「隠しファイルを含まない」なら、削除も検知しない）。設計書 5.1。
  - Windows では、消えたあとのファイルが隠しファイルだったかを確かめられない。手がかりは、覚えている中身にあったかだけ。隠しファイルは初めから外れているので、覚えている中身に入っていない。覚えるもの（論点 Y）を増やさずに済む。
  - あとから隠し属性が付いたら削除、外れたら作成として扱う。上の「条件の外から中への名前変更は作成」と同じ考え方。付いたときに覚えている中身から消さないと、あとで消したときに削除が出てしまう。
  - 属性を確かめる前に消えた作成は、隠しファイルではないとみなす。分からないときは、一瞬来たことも検知ログに残す（設計書 5.4）ほうに合わせる。
- 残り：用語集の「フィルタ」（当時の定義は「パスを、名前やパターンで絞り込む条件」）を監視フォルダの絞り込みにも使うか、言葉を分けるか。
- 残り（宿題一覧）：絞る条件の書き方。

## U. トリガーが見張る監視フォルダは 1 つか（決定）

- 用語集のトリガーの定義「どの監視フォルダで」は、1 つとも複数とも読めた。
- 決定：1 つのトリガーが見張る監視フォルダは、1 つだけにする。1 つの監視フォルダには、トリガーを 0 個以上書ける（論点 T）。
- 理由：
  - 変化の種類を複数使いたい場合（作成と変更、など）は、1 つのトリガーに複数書けば足りる。
  - 複数の監視フォルダで同じジョブを使うことは、まず無い。必要になったら、トリガーを分けて書き、同じジョブを指せばよい（ジョブは使い回せる）。
- 決定：1 つのトリガーに、変化の種類を複数書ける。
- 監視フォルダにも ID を付ける。トリガーが監視フォルダを指すため。
- 決定（あとで追記）：トリガーは監視フォルダの外に書き、監視フォルダを ID で指す。上の「1 つの監視フォルダには、トリガーを 0 個以上書ける」は、「1 つの監視フォルダを指すトリガーは 0 個以上でよい」という意味（設計書 4 章）。
  - 理由：設定の形を正規化できる。ジョブも ID で指すので、形が揃う（Roze：設定ファイルの構成は複雑でもよいが、正規化するなら、この形が最もよい）。
  - Roze の意見：ID を利用者が自分で定義するのは不自然なので、名前のようなものでもよいかもしれない（ID の付け方は宿題一覧 4.1）。
- 残り：用語集のトリガーの定義を、この決定に合わせて書き直す。→ 済み（2026-10-20、用語集に反映）

## V. 待ち表で待つものと、取りこぼしの扱い（決定。書き込み完了待ちの位置は仮決め）

- きっかけ：文書の突き合わせ（用語の番人と設計の検証役）の指摘。
  - 設計書 5 章の「待ち表で待つ」が、用語集の書き込み完了待ち（ランを始める前）・待ち表の定義と合っていない。
  - 発火中に届いた変化を捨てると、困る場面がある。
  - 再スキャンで見つけた違いを変化にするかが、設計書の 2 章では決まったこと、5 章では決めることになっている。
  - ランが起こした変化でもとのトリガーが発火しないことが、無視に当たるのか書いていない。
- 仮決め：書き込み完了待ちは、トリガーに合ったあと、発火の前に、待ち表で待つ。
  - トリガーに合わないパスは、書き込みの終わりを待たない。ジョブが無いので、待つ意味が無い（Roze）。
  - デバウンスの続きで待つ案（トリガーに合うかを見る前に待つ）は、ジョブの無いファイルまで待つことになるので採らなかった。
  - 待っている間は、ワーカーを使わない。
  - 仮決めの理由：Roze は、アプリの負荷が高くならないか心配している。確かめるのはトリガーに合ったパスだけで、Windows ではファイルを開けるかをときどき試し、Linux では OS が「書き込みのために開いていたプログラムが閉じた」と知らせる。ネットワークドライブでは 1 回の確認が遅い。実装で負荷を確かめてから決める。
- 決定：同じパスの発火が動いている間に、そのパスの次の変化が届いたら、捨てずに待ち表で待たせる。今の発火が終わってから、もう一度発火する。
  - 待っている間に同じパスの変化が何度届いても、待ち表の 1 行にまとめる。走るのは 1 回。
  - 理由：捨てると、アップロードしている間にもう一度保存したファイルが、古い版のまま残る（Roze：そのジョブが終わってから実行するべき）。
  - 起きる場面の例：アップロード中に人がもう一度保存する。ずっと書き足されるファイル（ログなど）。来てすぐ消えたファイルの、作成と削除の 2 つ（設計書 5 章）。
  - 前の決まりが変わる：論点 H の「実行中に届いた変化を無視する」と、用語集の無視の例「発火中に同じパスの変化が届いた」。
- 決定：溢れのあとの再スキャンで見つけた違いも、起動時の比較と同じく、変化として扱う（トリガーに合えば発火する）。溢れで取りこぼした分を取り戻すため。
- 決定：ランが起こした変化で、そのランのもとになったトリガーが発火しないこと（設計書 5 章）は、無視に当たる。理由「自分が起こした変化」を添えて、通知として流す。どのログに残すかは、ほかの変化の段階の無視と一緒に決める（論点 Q の残り）。→ 決定（論点 Q に追記。2026-10-20）
- 残り：用語集の書き込み完了待ち・待ち表・無視・再スキャン・変化の定義を、この決定に合わせて書き直す。→ 済み（2026-10-20、用語集に反映）
- 残り（宿題一覧）：待っている間に届いた変化を 1 行にまとめるときの、変化の種類の決め方。書き込みが終わったかを確かめる間隔。
  - 決定（あとで追記）：デバウンスと同じ「はじめとおわり」でまとめ、発火するときに、まとめた結果でトリガーに合うかを見直す。はじめもおわりも「無い」（作成のあと削除された）なら、差し引きで何も起きていないので、何も走らせずに行を消す。これは無視に当たる（理由「作成のあと削除された」）。検知ログには作成と削除が残る。確かめる間隔は、監視フォルダごとに変えられる（設計書 5 章）。
    - 理由：待ち表は何を走らせるかを決める所なので、来て消えただけのファイルに、アップロードや「クラウドからも消す」を走らせない。デバウンスで作成と削除の 2 つを残すのは、検知ログに「一瞬来た」ことを残すため。
- 決定（あとで追記、2026-10-20）：溢れたら、すぐには再スキャンせず、落ち着いてから 1 回だけ行う。最後の溢れや OS イベントから数え直し、一定の時間なにも届かなくなったら、監視フォルダ全体を再スキャンする。落ち着かなくても、一定の時間がたったら 1 回行う（設計書 5.2）。
  - 理由：溢れるのは、大量のコピーなどで忙しいとき。溢れるたびにすぐ再スキャンすると、重いコピーの最中に、何度もフォルダ全体を読み直すことになる。デバウンスと同じ考え方（Roze）。
- 決定（あとで追記、2026-10-20）：待ち表に行があるパスに届いた変化は、どのトリガーにも合わなくても、その行にまとめる（設計書 5.9）。
  - 理由：合う変化だけをまとめると、行の「はじめとおわり」が本当の様子とずれる。例：作成のトリガーが無いとき、アップロード中に届いた削除（cloud-delete に合う）と、ごみ箱から戻した作成（どれにも合わない）。作成をまとめないと、行は削除のままで、手元にあるファイルがクラウドから消える。まとめれば変更 1 つになり、アップロードが走る。

## W. 名前変更のまとめ方と、デバウンスを残すか（決定）

- きっかけ：設計書 5 章の決めること「名前変更のまとめ方」。名前変更は 2 つのパスにまたがるので、デバウンスでどうまとめるかが決まっていなかった。
- 決定：名前変更は、ほかの OS イベントとまとめない。名前変更 1 つとして残し、そこが区切りになる。作成・変更・削除は、区切りの前と後で、それぞれ「はじめとおわり」でまとめる（設計書 5 章）。
  - 例：名前を変えたすぐあと（デバウンス時間の中）に書き込みが来たら、名前変更 1 つと変更 1 つになる。
  - 理由：名前変更は名前変更として取りたい。同時に起きた名前変更と変更は、別にしたほうが、そのあとのジョブを正確に設定できる（Roze）。
  - 経緯：はじめは、元のパスが「ある → 無い」、新しいパスが「無い → ある」のときだけ名前変更 1 つとし、ほかは「はじめとおわり」の中で数える案だった。この案だと、仮の名前で書いてすぐ名前を変えたファイルは作成になり、Word の保存は変更 1 つになるなど、場合によって決まりが分かれる。Roze が「完全に統一したほうがよい」と言ったので、名前変更を区切りにする形にした。
- 決定：監視フォルダの条件で絞るのは、デバウンスの前（OS イベントの段階）。
  - 片側が監視フォルダの条件の外の名前変更は、作成か削除になり（論点 T）、それがデバウンスでまとめられる。
  - そのため、まとめた結果は監視フォルダの条件で変わる（Roze が気づいた）。例：Word の保存（一時ファイルとの入れ替え）は、一時ファイル（`~*` など）を条件で外していれば、元のファイルが「消えて → 現れた」としか見えないので変更 1 つになる。外していなければ、名前変更などがそのまま見える。
  - 前の決まりが変わる：設計書 5 章の「Word などの保存は変更 1 つ」は、「一時ファイルを外していれば変更 1 つ」になる。
- 決定：デバウンスは残す。デバウンス時間は監視フォルダごとに変えられ、0 にするとデバウンスしない（OS イベント 1 つが変化 1 つ）。
  - Roze は「そもそもデバウンスしない」案も考えた。やめると、しくみが簡単になり、待たずに反応し、OS が知らせたことが何も消えずに残る。
  - 残した理由：やめると困る場面がある。
    - 一時ファイルを外した監視フォルダで Word の保存をすると、削除と作成の 2 つになり、削除のトリガー（例：バックアップからも消す）が動いてしまう。
    - Linux で大きなファイルをコピーすると、書き込みのたびに OS イベントが届くので、検知ログが数千行になる。
    - 直接上書きでは Changed が 2 回届くので、変更が 2 つになる。
  - 「ばらばらに検知したい」場面のために、0 も選べるようにした。
- 残り：用語集のデバウンス・変化の定義を、この決定に合わせて書き直す（名前変更はまとめない、デバウンス時間は 0 もある）。→ 済み（2026-10-20、用語集に反映）
- 残り（宿題一覧）：デバウンス時間の既定の値。

## X. フォルダごとの変化と、見る深さ（決定）

- きっかけ：設計書 5 章の決めること「フォルダの変化」。Roze：監視フォルダには、ファイルだけでなくフォルダも来る。cat-watcher でも、フォルダを指定したトリガーで、フォルダの作成と、その中のファイルの作成を分けるかが紛らわしかった。
- 決定：フォルダごと入ってきた・名前が変わった・消えたときは、フォルダ自身の変化に加えて、中のパス（ファイルもフォルダも、見る深さまで）1 つずつにも、同じ変化があったとして扱う（会話では「展開」と呼んだ）。
  - 理由：OS は、フォルダごとの移動・名前変更・ごみ箱への削除では、中のパスについて何も知らせない。コピーや Shift+Delete では 1 つずつ知らせる。そのままだと、同じことをしても、やり方でジョブが走ったり走らなかったりする。フォルダごとでも 1 つずつでも、同じ結果にする（論点 W と同じ、統一の考え方）。
  - Roze の心配「展開は処理が難しくないか」：入ってきたときは、フォルダの中を読む（起動時の比較・再スキャンと同じしくみ）。名前が変わった・消えたときは、中身がもう見えないので、Foxonar が覚えている中身（前回の状態）から作る。新しく作るしくみは少ない。先例：Facebook の Watchman も、中身を覚えておき、1 つずつ知らせる。
- 決定：検知とトリガーを分ける。検知では、フォルダも中のパスも、1 つずつ別の変化にする。どれに反応するかは、トリガーで選ぶ。トリガーには、反応する対象（ファイル、フォルダ、両方）を書ける。
- 決定：深さは数で書く（Roze：`**` のようなパターンより直感的）。監視フォルダのすぐ下を 1 段目と数える。
  - 監視フォルダの「見る深さ」：どこまで検知するか。書かなければ制限なし。cat-watcher の「サブディレクトリまで見るか」は、1 段目までか制限なしかに当たる。
  - トリガーの「反応する深さ」：検知したもののうち、どこまでに反応するか。書かなければ、見る深さまで全部。同じ監視フォルダで、トリガーごとに深さを変えられる（例：フォルダのトリガーはすぐ下だけ、`*.txt` のトリガーは全部）。
  - トリガーの側にも置く理由：監視フォルダの側だけにすると、深さの違う監視フォルダを同じ場所に 2 つ作ることになり、検知ログに同じ変化が 2 行ずつ残る。
  - フィルタの名前のパターンは、名前だけに当てる。深さはパターンでは書かない。
- 残り：用語集の監視フォルダ（「サブフォルダまで見るかどうか」→ 見る深さ）とトリガー（反応する対象と深さ）の定義を書き直す（済み：2026-10-20、用語集に反映）。「展開」を言葉にするか。
- 決定（あとで変更、2026-10-20）：フォルダの名前が変わったときは、フォルダ 1 つの名前変更だけにする。中のパスの名前変更は作らず、覚えている中身のパスだけを書き換える。フォルダが入ってきた（作成）・消えた（削除）ときは、今のまま中のパスまで扱う。
  - 理由：フォルダの名前変更は、利用者やプログラムがフォルダ名を変えただけで、中のファイルの名前を変えたわけではない。ファイル名は変わっていないのに名前変更が出るのは過剰（Roze：`C:\Program` を `C:\Program2` にしたら、配下すべてに名前変更が来るのはおかしい）。
  - 結果：中のファイルを 1 つずつドラッグで別のフォルダへ移すと、OS が名前変更として知らせるので名前変更になる。フォルダの名前を変えたときとは、結果が違う。
- 残り（宿題一覧）：名前のパターンの書き方。

## Y. 変化のもとと、覚えている中身・再スキャン・中断（決定）

- きっかけ：2026-10-20 の文書の突き合わせ（用語の番人と設計の検証役）の指摘。
  - 変化の生まれ方に、フォルダが消えたときに覚えている中身から作る、中のパスの削除が入っていない。フォルダの中を読んで作った作成と、OS から届いた同じパスの Created を、デバウンスでまとめられない（デバウンスは OS イベントだけをまとめる定義だった）。
  - 「前回の状態」が、止める前の中身と、動いている間の今の中身の 2 つの意味で使われていた。
  - 「中断」が用語集に無く、設計書 6.3 の「途中で止められたら失敗」と 2.5 の「中断」が食い違っていた。
  - 発火の定義「合ったときに始まる」が、待ち表で待ってから発火する決まり（論点 V）と合わなかった。
  - 待ち表でまとめると、論点 W の「名前変更と変更を分ける」が消える。まとめた変化のどれをランにつなぐかも決まっていなかった。
- 決定：監視フォルダに何があるかの記憶を「覚えている中身」と呼ぶ（「前回の状態」はやめる）。検知するたびに更新し、コアを止めても残る。
  - 宿題一覧の「前回の状態をいつ更新するか」は、これで「検知するたびに」に決まった。
- 決定：フォルダを読み直し、覚えている中身と比べることを、すべて「再スキャン」と呼ぶ。起動したとき（これまでの「起動時の比較」）、溢れのあと、フォルダが入ってきたときに行う。
- 決定：変化のもとは 3 つ。OS イベント、再スキャンで見つけた違い、覚えている中身から作ったもの（フォルダが消えたときの中のパス）。どれもデバウンスを通し、同じパスなら 1 つにまとめる。
  - 理由：フォルダがコピーで来たとき、中を読んで作った作成と、OS から届いた Created が別々の 2 行になるのはおかしい（Roze：作成されていないのに 2 行出るのはおかしい）。
- 決定：「中断」を用語にする。Foxonar の側の事情（コアを止めた、コアが落ちた）で、ランが最後まで走らなかったこと。Foxonar の外から止められたとき（タスクマネージャー、シグナルなど）は失敗。
- 決定：発火の定義を短くする。トリガーに合った変化から、そのトリガーのジョブを走らせること。いつ始まるかは用語集に書かず、設計書（待ち表）に任せる（Roze：発火までは細かく定義をする必要はない）。
- 決定：待ち表でも、名前変更は区切りにする。名前変更のあとに届いた変化は、別の行にして、名前変更の発火が終わってから順に発火する（論点 W と揃える）。
- 決定：待ち表で 1 行にまとめた変化は、最後の変化の検知 ID だけをランに書く（Roze）。それより前の変化の行からは、ランへたどれない。
- 残り：用語集の発火・デバウンス・変化・再スキャンの定義を直し、覚えている中身・中断を足す。→ 済み（2026-10-20、用語集に反映）
- 決定（あとで追記、2026-10-20）：覚えている中身には、パスごとに、ファイルかフォルダか、大きさ、更新日時を覚える。再スキャンでは、この 3 つとパスで比べる（設計書 5.2）。
  - 理由：大きさと更新日時があれば、止まっている間に上書きされたファイルも変更として見つかる（rsync や Syncthing と同じ見分け方）。覚えるものを増やすと、処理が重くなるので避けたい（Roze）。
  - 採らなかったもの：ファイル ID（止まっている間の名前変更も見分けられるが、USB メモリや一部のネットワークドライブでは毎回変わる）、中身の指紋（起動のたびに全部のファイルを読むので遅い）。そのため、止まっている間の名前変更は、今までどおり削除と作成に見える。
- 決定（あとで追記、2026-10-20）：止まっている間に起きたことの扱い（再スキャンするか、何もしないか）と、覚えている中身が無いときの扱い（覚えるだけか、すべて作成か）は、監視フォルダごとに必ず書く。既定の値は持たない。書いていない設定は、読み込みの失敗になる（設計書 5.2）。
  - 理由：書かないという選択肢は無い（Roze）。どちらを選んでも、ジョブが走るか走らないかが大きく変わるので、利用者が選ぶ。
- 決定（あとで追記、2026-10-20）：止まっている間に起きたことの選択肢「何もしない」は「覚えるだけ」と呼ぶ。起動したときに中を読み、覚えている中身を今の様子に合わせるが、違いは変化にしない。再スキャンではない（設計書 5.2）。
  - Roze の問い：中身を覚えておく意味を考えると、何もしないフォルダは覚え直す必要はないのでは？
  - 答え：覚えている中身は「今、監視フォルダに何があるか」の記憶で、動いている間にも使う（隠しファイルの削除の見分け、溢れのあとの再スキャン、フォルダが消えたときの中のパス）。古いままだと、溢れた日の再スキャンで、止まっている間に起きたことまで変化として出て、ジョブが走ってしまう。覚え直しても、止まっている間に起きたことは変化にならないので、「何もしない」の意図は守れる。
  - 名前は、覚えている中身が無いときの「覚えるだけ」と同じ動きなので揃えた。

## Z. フォルダの作成で、中身が揃うのを待つか（決定）

## AA. 監視フォルダそのものが消えたとき（決定）

- きっかけ：2026-10-21 の段階 0 の実験（監視フォルダが消える）で、監視フォルダそのものが消えたとき・名前が変わったときの決まりが、設計に無いことが分かった（Roze：考慮漏れ）。
  - 実験で分かったこと：Windows（notify）は、監視フォルダを消すと中のファイルの削除だけを知らせ、監視フォルダ自身のことは知らせない。名前を変えても何も知らせない。Linux は、監視フォルダ自身の削除・名前変更も知らせる。
  - どちらの OS も、名前を変えた先の変化を、もとのパスとして知らせる。同じ名前で作り直しても、見張りは戻らない。
  - 起きる場面：USB メモリを抜いた、ネットワークドライブが切れた、人が監視フォルダを消した・名前を変えた・ごみ箱に入れた。
- 決定：監視フォルダそのものが、消えたり、名前が変わったり、つながらなくなったりして、見張れなくなることを「見失う」と呼び、用語にする。中のファイルが消えたこと（削除）とは区別する。
- 決定：見失ったことには、一定の間隔（数秒）ごとに「まだあるか・見張りを始めたときと同じフォルダか」を確かめて気づく。Linux では、OS の知らせ（監視フォルダ自身の削除・名前変更）でも気づく（Roze）。
  - 理由：USB やネットワークが切れたときも、同じしくみで気づける。
  - Roze の問い：OS の知らせを待っている間にパスが消えても気づけないので、ポーリングするしかないのか？
  - 答え：Windows は、監視フォルダの名前を変えても OS が何も知らせない（見張りがフォルダについて行く）ので、確かめに行くしかない。消したときは OS が知らせるが、notify が捨てている。確かめるのは監視フォルダのパス 1 つだけで、中は読まないので軽い（例：監視フォルダ 10 個を 3 秒ごとなら、1 秒に 3 回）。
  - 採らなかったもの：1 つ上のフォルダも見張る（上のフォルダごと消えると気づけない）。
- 決定：見失っても、中のパスを削除の変化にしない。アプリログと Web UI で見失ったことを知らせ、その監視フォルダの見張りを止める。覚えている中身は残す（Roze）。
  - 理由：削除にすると、USB を抜いただけで、削除のトリガー（クラウドからも消す、など）が中のファイルすべてに走る。
  - 人が本当に監視フォルダを消したときは、OS が中のパスの削除を知らせてくるので、それは今までどおり削除の変化になる。
  - 採らなかったもの：中のパスをすべて削除の変化にする（設計書 5.6 の、フォルダが消えたときと同じ扱い）。
- 決定（あとで追記、2026-10-21）：見失ったら、その監視フォルダの待ち表の行と、発火したがまだ始まっていないランを消す。走るはずだったジョブごとに、ランログに「無視」（理由「監視フォルダを見失った」）の行を書く。走っているランは止めない（Roze：待ち表とかからもデータを消す）。
  - 理由：「なぜジョブが走らなかったか」は、全部ランログで分かるようにする（設計書 7.2 の考え方）。
- 決定（あとで追記、2026-10-21）：検知ログに、見失ったときと、また現れたときに 1 行ずつ残す。溢れの行と同じ形で、変化の種類の列に「見失った」「また現れた」と書く（Roze：監視フォルダが消えたことを明示する）。
  - 理由：検知ログだけ見ていても、その間の抜けに気づけるようにする。
- 決定（あとで変更、2026-10-21）：同じパスに監視フォルダがまた現れたら、自動で見張り直す。中にあるものは、覚えている中身に入れるだけで、変化にしない（設計書 5.2 の「覚えるだけ」と同じ動き）。監視フォルダごとの 5.2 の選び方には従わない（Roze：最初にあったファイルはすべて無視）。
  - 前は「5.2 の選び方（再スキャンする・覚えるだけ）に従う。ただし、覚えている中身にあって無くなっていたパスは、削除の変化にせず忘れる」だった。
  - 理由：別の USB メモリを挿したときなどに、前のファイルがすべて削除に見えたり、中のファイルがすべて作成に見えたりするのを防ぐ。
  - そのため、見失っていた間に置かれた・変えられた・消されたファイルは、変化として出ない。
  - 採らなかったもの：5.2 の選び方に従う（前の決定）。5.2 の選び方どおり、無くなっていたものも削除にする。フォルダの背番号（ファイル ID）で違うフォルダと分かったら、覚えている中身が無いときの扱いにする（同じ USB メモリでも、挿し直すと背番号が変わることがある）。自動では戻さず、利用者が Web UI や CLI で戻す。
- 残り：用語集に「見失う」を足す。→ 済み（2026-10-21、用語集に反映）
- 残り：用語集の検知ログの定義に、見失った・また現れたの行を足す。→ 済み（2026-10-21、用語集に反映）
- 残り（宿題一覧）：確かめる間隔の既定の値、同じフォルダかの見分け方、起動したときに監視フォルダが無いときの扱い。

## AB. 削除のステップで、ごみ箱をやめる（決定）

- きっかけ：2026-10-21 の段階 0 の実験（ごみ箱）。ごみ箱に入れるクレート（`trash`）は、Windows のネットワークの場所では、成功と返したのに、ごみ箱に入れずに消した。設計書 4.4 の「ごみ箱が使えない場所なら、すぐ消さずに失敗にする」は、そのままでは作れない。
  - Linux では失敗にならず、そのドライブに `.Trash-1000` を作るか、ホームのごみ箱へ中身をコピーする。
- 決定：削除のステップは、いつもすぐ消す。ごみ箱には入れない（Roze：しくみ的に厳しいなら、ごみ箱に入れるのはやめてもいい）。
  - 消えてほしくないときは、削除の代わりに、移動で退避用のフォルダへ移す。
  - 理由：ごみ箱が使えない場所の見分け、サービスで動かすと別のユーザーのごみ箱に入る、画面の無いサーバーではたまり続ける、といった注意がすべて無くなる。
  - 採らなかったもの：ローカルのドライブだけごみ箱を許し、消す前にドライブの種類を調べて、ネットワークなら失敗にする。
