# 宿題一覧

まだ決めていないことと、その案です。章立ては [設計書](design.ja.md) と同じです。

- 決まったら、設計書の節にやり方と理由を書き、ここから消す。言葉を足す・変えるときも、ここに書いて話す。
- 「案」は、まだ決定ではない。
- 言葉は [用語集](glossary.ja.md) の意味で使う。
- 最後の「いつか」と「実装してから」の表には、今は決めないものを分けて置く。
- 日本語のみ。

## 2. 全体の構成

| 項目 | 決めること |
|---|---|
| 起動の登録 | ログイン時の起動とサービスを、どう登録するか（Windows のスタートアップかタスク スケジューラか、Windows のサービス、Linux の `systemctl --user` と systemd）。CLI で登録できるようにするか |
| 二重起動の防止 | しくみ（案：設定ファイルの隣に印用のファイルを置き、OS のファイルロックで 2 つ目のコアを止める）。2 つ目が起動しようとしたときの扱い（案：アプリログに残して終わる） |
| CLI とコアのやりとり | CLI がコアにどうつながるか（Web UI と同じ API を使う、など） |
| 猶予の間に届いた変化 | 止め始めてから止まるまで（猶予の間）と、止め始めたときにデバウンス中だったものを、どう扱うか（設計書 2.5）。例：「覚えるだけ」の監視フォルダで、17:59:59 に cat.jpg（デバウンス中）、止め始めた 18:00:05 に dog.jpg を置くと、今のままでは、次に起動しても 2 枚とも検知ログに出ず、ジョブも走らない。案：(a) 止め始めたら見張りもやめ、「止まっている間」とする (b) 猶予の間も見張って検知し、トリガーに合えば待ち表に入れる |

## 3. Web UI

| 項目 | 決めること |
|---|---|
| 作り方 | Rust の Web のフレームワークで作りたい。有力な案：Topcoat（tokio のチームが 2026-07 に出した。HTML はサーバーで Rust が作り、画面の一部だけを書き換える。コアと同じ tokio の上で動く。まだ 0.x で、書き方が変わる段階。Windows（gnu 版）で動くかは、試して確かめる）。ほかの候補：axum＋htmx、Leptos や Dioxus（画面も Rust で書き、WASM にする）、素の HTML＋JavaScript |
| ポート | 番号。設定で変えられるか。使われていたらどうするか。コアを複数動かすときは、コアごとに別の番号が要る |
| 守りの具体 | トークンの作り方、置き場所、利用者への渡し方（案：CLI で表示する、起動時にトークン付きの URL を表示する）。CSRF と DNS リバインディングへの備えの具体（案：要求の `Host` と `Origin` を確かめる） |
| 画面の一覧 | どんな画面を持つか。待ち表の行を見せるか。自動で更新するか（今動いているランと、同時実行数や依存先で待っているランは、ランログで見える。設計書 7.2）。メニューの 5 つは決まった（設計書 3.3）。案：見本 [external-design/webui.html](external-design/webui.html)（ブラウザで開く）のとおり、ほかに合言葉の画面・コアを止めている間の画面。待ち表も見せ、自動で新しくする。画面ごとの案は、見本の上の「説明を出す」で見られる |
| 大量のときの見せ方 | 畳むこと・フォルダを 1 階層ずつ出すことは決まった（設計書 3.3）。見本の案：同じ監視フォルダの同じ一番上のフォルダに、30 秒以内に続けて 5 個以上来た同じ種類の変化を、1 つのまとまりに畳む（数と、ランの結果の帯を出す）。ランログでは、そのまとまりから走ったランを、トリガーごとに畳む。10 分ごとの棒（数の平方根の高さ）を押して時間を絞る。フォルダごとの見方は 50 個ずつ出し、パンくずが長いときは途中を「…」にする。成功しなかったランは、ジョブと理由でまとめる。設定の一覧とつながりには「探す」欄を付ける。30 秒・5 個・50 個は仮の値 |
| 設定の画面 | つながりを図と表で見ることは決まった（設計書 3.3）。見本の案：つながりを探す欄で絞ると、図では合うものとつながるものだけを出す。表は定義順に並べ、トリガーの無い監視フォルダと、どのトリガーからも走らないジョブを下に出す。フィルタをその場で試せる。プレースホルダが置き換わった例を見せる。ID は作ったあとは変えられない（変えると別のものとして扱われる。設計書 9.3）。指しているトリガーがある監視フォルダ・ジョブは消せない |
| 読み込みに失敗している間 | 設定の読み込みに失敗している間（設計書 4.2）、設定の画面で何を見せ、直せるようにするか（見本の案：今動いている前の設定を、直せない形で見せ、壊れた行を見せる） |

## 4. 設定ファイル

### 4.1 ファイルの扱い

| 項目 | 決めること |
|---|---|
| 置き場所 | 設定ファイル、SQLite のファイル、アプリログ、出力のファイルを、どこに置くか。ログイン時に起動する場合とサービスの場合で変わるか |
| Web UI から書くとき | 書きかけのファイルをコアに読ませない方法（案：一時ファイルに書いてから名前を変える）。コメントと並び順を残す方法（案：`toml_edit` クレートを使う） |

### 4.2 設定の中身

- 設定ファイルにどう書くか（キー名や書き分け方）は、9 章の「設定ファイルの形」で一緒に決める。

| 部品 | 決めること |
|---|---|
| プレースホルダ | 安全のための決まり（この一覧の 4.3。書き方と一覧は決まった。設計書 4.4） |
| プロセス実行 | プログラムを確かめるタイミング（この一覧の 4.4 に案がある） |
| 依存の警告 | 組み込みの移動や削除のステップを持つジョブが、ほかのジョブと依存なしで並行になっているときの、警告の出し方（設計書 6.1） |
| 書かなかったときの扱い | 次のものを書かなかったとき、既定を持つか、必ず書かせるか（止まっている間の扱いと、覚えている中身が無いときの扱いは、必ず書く。設計書 5.2）。コピー・移動の「上書きする」（案：上書きしない＝失敗）と「行き先のフォルダが無ければ作る」。ジョブの「中断したランを自動でやり直すか」（設計書 6.6）。ジョブごとの同時実行数の上限（すぐ走るか、読み込み時にエラーか）と、全体の上限（必ず書かせるか、CPU の数などを既定にするか）（設計書 6.1） |
| 時間の既定の値 | この一覧の 4.5 の表の時間の、既定の値。利用者が変えられるようにするか |

### 4.3 プレースホルダの案

- 書き方と一覧（7 つと、日付・時刻・環境変数）は決まった（設計書 4.4）。
- 安全のための決まりの案：
  1. 置き換えは 1 回だけ行う。置き換えた値の中に `${env:HOME}` のような文字があっても、展開しない。
  2. プログラムの欄に `${path}` などランのプレースホルダを書いた場合（監視フォルダに置かれたファイルそのものを実行する場合）は、設定の読み込み時に警告する。監視フォルダに書き込める人なら誰でも、Foxonar の権限でプログラムを実行できるようになるため。禁止はしない。禁止しても `powershell -File ${path}` のように引数で渡せば同じことができ、防ぎきれないため。
  3. シェルにコードとして文字列を渡すオプション（`sh -c`、`cmd /C`、`powershell -Command` など）の引数にプレースホルダを書いた場合は、設定の読み込み時に警告する。`powershell -File` のようにスクリプトのファイルを渡す使い方は対象外。
  4. 文字としての `${` を書きたいときのエスケープの方法を決める（`$${` など）。

### 4.4 プロセス実行の案

- プログラムを確かめるタイミングの案：
  - プログラムの欄にランのプレースホルダが無い場合：設定の読み込み時（コアの起動時と、設定を読み直したとき）に探してフルパスに決める。見つからなければ、設定の読み込みの失敗と同じ扱いにする（設計書 4.2）。決めたフルパスは、通知として流す。
  - プログラムの欄にランのプレースホルダがある場合（監視フォルダに置かれたファイルそのものを実行する場合など）：設定の読み込み時にはまだ存在しないので確かめない。ランの実行時に確かめ、見つからなければそのステップの失敗にする。

| デバウンス時間 | 5.4 | |
| 溢れのあと、落ち着いたとみなすまで | 5.2 | |
| 溢れのあと、落ち着かなくても再スキャンするまで | 5.2 | |

## 5. 監視と検知

| 項目 | 決めること |
|---|---|
| 書き込み完了待ち | 判定の方法（OS で違う。Linux には「書き込みのために開いていたプログラムが閉じた」という知らせがあり、Windows には無い）。削除の変化でも待つか（案：待たない。待つファイルが無いため） |
| 発火を待つ順番 | 同じパスに 2 つのトリガーが合い、1 つ目の発火の間に同じパスの変化が届いたとき、2 つ目の発火（まだ動いていない）と、待ち表の新しい行を、どの順に動かすか。まとめるか（設計書 5.9、6.1）。止めたときに、2 つ目の発火を残すか（設計書 2.5 の「まだ始まっていないもの」に入っていない）。例：トリガー X（backup）と Y（upload）が report.xlsx の変更に合う。X の間にもう一度保存した。案：(a) 順番どおり（Y、そのあと待ち表の行で X と Y） (b) まだ動いていない Y の発火を、待ち表の行にまとめる |
| ネットワークのフォルダ | Linux でネットワークのフォルダ（SMB・NFS など）を見張ると、OS イベントが届かないことがある（2026-10-21 の実験で、WSL の `/mnt/c` で確かめた。定期的に読み直す見張りなら拾えた）。Windows でも、`\\wsl.localhost\...` では、新しい版・古い版の見張りの命令のどちらも、OS イベントが届かなかった（設計書 5.12）。定期的に読み直す見張りを使うか、いつ使うか（案：監視フォルダごとに選べる） |

## 6. ランの実行

| 項目 | 決めること |
|---|---|
| やり直しと依存 | 中断したランを自動でやり直すとき、そのランに依存して「待っている」ランをどうするか。やり直しのランと「待っている」ランの、どちらを先に動かすか。やり直しのランに書く検知 ID（設計書 6.6）。例：ジョブ convert（中断したらやり直す）に、ジョブ notify（Slack に知らせる）が依存。変換中に PC を再起動 → ラン 45（convert）は中断、ラン 46（notify）は待っている → 起動するとやり直しのラン 47 ができる。案：(a) ラン 46 は 47 を依存先として待つ (b) ラン 46 は無視（依存先が成功しなかった） (c) 発火ごと、新しいラン ID で作り直す |
| 落ちたときの書きかけ | コアが落ちたとき、コピー・移動の書きかけの行き先が残る（止めたときは消してから止める。設計書 6.5）。やり直しが「上書きしない」で失敗する。例：4 GB のコピー中に停電 → 書きかけの `D:\backup\video.mp4` が残る → やり直しのランは「行き先に同じ名前がある」で失敗。案：(a) 今のまま（利用者が消してから、もう一度変化を起こす） (b) 起動したときに、中断したランが書いていた行き先を消してからやり直す (c) コピーは仮の名前で書き、終わってから名前を変える |
| フォルダとその中の発火 | フォルダのトリガーと、中のファイルのトリガーの発火は、パスが違うのでロックが別々で、同時に走る。フォルダのジョブがフォルダを移動・削除すると、中のファイルのランが無視や失敗になる（設計書 5.6、6.1）。例：トリガー F（フォルダ・作成 → zip にして `D:\done\` へ移動）と T（ファイル・作成・`*.txt` → 中身を Slack に送る）。案：(a) 今のまま（利用者の責任） (b) フォルダの発火は、中のパスの発火が終わるまで待つ (c) 設定の読み込み時に警告する |

## 7. ログ

| 項目 | 決めること |
|---|---|
| 「すべて作成として扱う」の見つけ方 | 覚えている中身が無いときに「すべて作成として扱う」で出た変化（と、見る範囲を広げたときの変化）の、検知ログの「見つけ方」の列に何を書くか。フォルダも作成にするか（設計書 5.2、7.2）。例：たまった写真 1,200 枚の監視フォルダを足すと、10:00 に 1,200 個が置かれたように見える。案：(a) 空にする (b) 新しい値（「すべて作成として扱う」など）を足す |
| Linux で溢れたときの行 | inotify はどの監視フォルダで溢れたかを知らせない（設計書 5.2）。検知ログの溢れの行の、監視フォルダ ID とパスに何を書くか（設計書 7.1）。案：(a) 監視フォルダごとに 1 行ずつ (b) 1 行だけで、監視フォルダ ID とパスは空 |
| 保存期間と分け方 | 検知ログ・ランログ・アプリログ・出力のファイルを、何日分・何件分残すか。ログごとに期間がずれると、片方からもう片方をたどれなくなる。アプリログの分け方（日ごとにファイルを分ける、など） |
| OS のログ | サービスのとき、OS のログ（Windows のイベントログ、Linux の journald）にも出すか |

## 9. 作り方

| 項目 | 決めること |
|---|---|
| 設定ファイルの形 | ファイルの分け方・全体の形・最小の流れで読むキー（ID・名前・パス・変化の種類・フィルタ・ジョブ・プロセス実行）は決まった（設計書 9.6）。残りのキー名と書き方：全体の設定、見る深さ、監視フォルダの条件、デバウンス時間、止まっている間の扱いと覚えている中身が無いときの扱い（2 つとも必ず書く。設計書 5.2）、反応する対象と反応する深さ、組み込みのステップ（コピー・移動・削除）、成功とみなす終了コード（0〜7 のような範囲。設計書 6.3）、依存（GitHub Actions の `needs` のように依存先を並べる、など。設計書 6.1）、止めるときの猶予（設計書 2.5）、出力のファイルに残す標準出力の行数（全体に書くか、ジョブやステップごとに書くか。設計書 7.1） |
| ランの写しの消し方 | ランログの中だけの列（発火の束・依存先・ジョブの写し）を、いつ消すか。ランが終わったら消すか。中断したランを自動でやり直すとき（6.6）は、写しをやり直しのランに引き継ぐか（設計書 9.3） |

## 言葉

用語集を直す候補と、言葉の使い方の宿題。決まったら、用語集（と英訳）を直し、ここから消す。

| 言葉 | 決めること |
|---|---|
| 中断 | 定義「ランが最後まで走らなかったこと」は、まだ始まっていないランにも当てはまるように読める（設計書 2.5 では、待っているランは中断にしない）。「走り始めたランが、最後まで走り終わらなかったこと」にするか |
| 無視 | 定義の例「ランの直前に、対象パスにファイルが無かった」は、使わない言葉「ファイル（ランの対象として）」を使っている。「対象パスが無かった」にするか |
| Web UI | 定義「設定とログを見たり変えたりする画面」は、ログも変えられるように読める（設計書 3.2 では、ログは見るだけ）。「設定を見たり変えたり、ログを見たりする画面」にするか |
| 再スキャン | 定義「起動したとき、溢れのあと、フォルダが入ってきたときに行う」は、起動したときは「再スキャンする」を選んだ監視フォルダだけ（設計書 5.2）。「いつ行うか」を定義から外すか |
| 待ち表・書き込み完了待ち | 待ち表の定義「パスごとに 1 行を持つ表」は、名前変更・移動で区切ると、同じパスに行が並ぶ（設計書 5.9）。どう書くか。また、2 つの定義に、仮決めの「待つ位置」（トリガーに合ったあと。設計書 5.9）が入っている。決め直すと定義も変わる。定義を「発火する前に、書き込みが終わるのを待つこと」までにするか |
| OS イベント | 定義に命令の名前（ReadDirectoryChangesExW）があり、古い版（ReadDirectoryChangesW）に切り替えた監視フォルダ（設計書 5.12）が外れる。命令の名前を外し、設計書に任せるか |
| 同時実行数 | 定義「上限に達しているときだけ、ランは始まるのを待ち」は、依存先と、止めるときの猶予でも待つ（設計書 2.5、7.2）。「同時実行数のために待つのは、上限に達しているときだけ」にするか |
| フィルタ | 用語集の「フィルタ」を、監視フォルダの条件（設計書 5.1）にも使うか、言葉を分けるか |
| 並び順 | 覚えている中身の「検知するたびに」、トリガーとデバウンスの「移動」が、それを定義する変化（下の行）より上で使われている（使い方の決まり 15）。並べ替えるか、言い回しを変えるか |
| 知らせ | 設計書で、OS からの通知や OS イベントの意味で「知らせ」を使っている。言葉にするか、言い方の決まりに足すか |
| 出力のファイル | 設計書 7.1 の「ラン 1 回ごとの出力のファイル」は、3 つのログのどれでもない記録で、言い方の決まり「記録はすべてログ」とぶつかる。名前を付けるか、ランログの一部とするか。「Foxonar がファイルを出力するとき」（ジョブが作るファイル）とも読まれた（2026-10-25） |
| 発火する | 主語がばらばら（「変化は…発火する」「発火したがまだ始まっていないラン」「待っているパスは、まだ発火していない」「削除で発火したラン」）。どう言うか |
| ランログ | 定義「ラン 1 回分ごとの記録」と、発火しなかったときの無視の行（ランができていない）がずれる。その行にもラン ID を振るか |
| 通知 | 定義「Foxonar の中で起きたことの記録 1 件」と、言い方の決まり「記録はすべてログと呼ぶ」がぶつかる |
| 画面の名前 | Web UI の見本（external-design/webui.html）で付けた名前（今の様子、困りごと、かたまり＝一度にたくさん来た変化のまとまり、流れ・フォルダごと、つながり）を、言葉として決めるか。「困りごと」は、設計書で日常語として使っている（8 章） |
| 用語集の「意味だけ」 | 定義に「どうやるか」が入っている（プロセス実行の `.ps1` の起動のしかた、依存の警告、コアの Web サーバ、デスクトップ通知の「利用者が選ぶ」、覚えている中身の「止めても残る」）。設計書に移すか |

## いつか

設計で「あとで足す」とした機能や、設計にまだ無い機能の宿題。今は決めない。その機能を足すときに決める。

| 項目 | 決めること | いつ要るか |
|---|---|---|
| 証明書 | ほかの PC から接続するときの、証明書の用意のしかた（自分で作る、Tailscale を使う、など） | ほかの PC やスマホからの接続を足すとき（設計書 1.2、3.1） |
| サーバーでの代わり | サーバーで、デスクトップ通知の代わりに何で知らせるか（Webhook（Discord、Slack など）、メール、ntfy など） | その機能を足すとき（サーバーではデスクトップ通知を出せない。設計書 1.1） |
| 画面の英語 | Web UI の言葉を、英語に切り替えられるようにする方法 | 英語を足すとき（設計書 3.2） |

## 実装してから

動かして測らないと決められない宿題。実装してから決める。

| 項目 | 決めること |
|---|---|
| 書き込み完了待ちの位置 | 仮決めの待つ位置（トリガーに合ったあと、発火の前。設計書 5.9）を、実装で負荷を確かめて決め直す |
| ログの量 | 実装したら、ログの量を確かめ、要らない列や行（無視の行、溢れの行、ステップごとの記録、エラーの中身など）を削るか見直す（実際に作ったら情報量が多すぎて、「このログは要らない」となるかもしれない。設計書 7 章）。出力のファイルに残す標準出力の行数の既定（仮決め 50 行。設計書 7.1）も、実際のログを見て決め直す |
