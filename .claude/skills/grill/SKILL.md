# 設計を詰める（grill）

決めることを「木」にして、前提が決まったものから順に、Roze に聞いていく。

- もとにした考え方：mattpocock/skills の `grilling`（決めることの木を、聞ける所から回ごとに聞く）と `domain-modeling`（言葉のずれをその場で正し、具体例で試し、決まったらすぐ書く）。Foxonar の文書の形と、Roze の決まりに合わせて作り直した
- **決めるのは Roze。** Claude は問いを作り、調べ、具体例とおすすめを出し、決まったことを書く
- 書いたものどうしの突き合わせは、doc-check スキルの役目。このスキルは「決める」ほう

```
① 木を作る ─→ ② 今聞ける問いを選ぶ ─→ ③ 聞く ─→ ④ すぐ書く ─→ ⑤ 具体例で試す
                     ↑                                                   │
                     └──── ほころびが見つかれば、木に新しい問いを足す ───┘
聞ける問いが無くなったら、⑥ 分かり合えたかを確かめて終わる
```

## ⓪ 始める前に

- **ブランチ**：`git branch --show-current` で確かめる。main なら、決める範囲に合った名前のブランチ（例：`docs/run-result`）を main から切ってよいか、Roze に聞く（Roze：main だと、ほかの会話と競合することがある）
- **範囲**：Roze が言った範囲にする。言われなければ、宿題一覧のうち「動き方」（今の論理設計で決めるもの）を範囲にしてよいか、一言確かめる
  - 書き方・既定の値・作り方（Web UI など）は、物理設計と実装で決めるので、木の外に置く

## ① 木を作る

- 材料
  - 宿題一覧 `docs/todo.ja.md` の「決めること」（`python scripts/doc_check.py --todo` で一覧が出る）
  - 作業メモ `.claude/notes.md` の「まだやっていないこと」。前回の木があれば、その続きから始める
- 前提の関係：「A が決まらないと、B は当て推量でしか聞けない」なら、B を A の下にぶら下げる
- 木は、作業メモの「まだやっていないこと」に書く（下の「木の書き方」）。範囲の分だけにし、宿題一覧を全部は写さない

## ② 今聞ける問い（フロンティア）を選ぶ

- 前提がすべて決まっている問いだけを選ぶ
- 同じ回の中の別の問いの答えで変わる問いは、次の回に回す
- 5 つ以上あれば、流れの順（変化をつくる → 待つ → 走る → 残す）で先のものから 4 問まで。残りは次の回
- **調べれば分かることは、Roze に聞かない。** 問いに事実が要るなら、Claude が先に調べる
  - 文書に何が書いてあるか：自分で読む。広く探すなら Explore エージェント
  - OS やライブラリの動き：調べるか、実験する（例：2026-10-19、PowerShell の FileSystemWatcher で Word の保存を再現し、デバウンスのまとめ方を決めた）
  - 調べている間も、その結果に関係しない問いは先に聞いてよい
  - 調べた結果は、問いに「調べたこと」として添える

## ③ 聞く

- AskUserQuestion で、1 回に 4 問まで（Roze が選んだ形）
- 選択肢の説明に入りきらない話は、問いの前の本文に、図をまじえて書いてよい
- 1 問ごとに、本文か preview に次を書く
  - **具体例**：ファイル名・ジョブ名・トリガーの中身・時刻を入れた時系列。コードブロックの図にする
  - **用語の意味をひとこと**：その問いに出てくる言葉（例：「発火」＝1 つの変化に 1 つのトリガーが合ったときの、ひとまとまりの実行）
  - **なぜそう設定するのか**：利用者がその設定をする理由
  - **選んだら何が変わるか**：選択肢ごとに、上の例がどうなるか
  - **実際の見た目**：ログ・設定ファイル・表のように形があるものは、実際の行や書き方の見本を、「今のまま」と「選んだあと」の両方で見せる。矛盾を指摘するときも、説明より先に、それが起きる具体例を見せる（2026-10-20、Roze：ログは例がないと、今のままだとどんな行になるのか分からない）
- おすすめを先頭に置き、ラベルに「（おすすめ）」と付ける。おすすめを選べば、そのまま決まる聞き方にする

### 答えが返ってきたら

- 「分からない」「そもそも起きないのでは？」「どういう意味？」：言い直すより、例をもっと具体的にし、起きる場面を 2〜3 個並べて聞き直す
  - 例：2026-10-19、「発火中に届いた変化は？」が伝わらなかった。「アップロード中にもう一度保存」「ずっと書き足されるログ」「来てすぐ消えたファイル」を並べたら決まった
- 「あなたはどう思う？」：意見をはっきり言う。理由と、その案で上の例がどうなるかを添える
- Roze が別の案を出した：その案で例がどうなるかを確かめ、良い点と困る点を率直に言う。良ければ、そちらに乗り換える（例：書き込み完了待ちの位置は、Roze の「トリガーに合わなければ終わりでしょ？」の案になった）
- 「仮決め」「とりあえず」：仮決めとして書き、なぜ仮かも残す

### 言葉のずれは、その場で直す

- Roze の言葉が用語集とずれていたら、すぐ確かめる。用語集の言葉で言い直し、意味が合っているかを聞く
  - 例：OS イベントのことを「トリガー」「イベント」と言った。「デバウンス時間に複数のトリガーが走ったとき」→「複数の OS イベントが届いたとき、ですね？」
- 2 つの意味に取れる言葉は、どちらの意味か聞く
- 新しい言葉が要るとき、用語集の意味を変えるときは、宿題一覧に書いて聞く。用語集は、決まってから直す（AGENTS.md の決まり 4）

## ④ 回ごとに、すぐ書く

会話が要約されても失わないように、1 回ごとに書く（Roze が選んだ）。

| 決まったもの | 書く先 |
|---|---|
| どう動くか | 設計書 `docs/design.ja.md` の該当の小番号（x.x）の本文。書いたら、宿題一覧 `docs/todo.ja.md` から消す |
| なぜそうしたか | 本文に書いた以上の理由・採らなかった案・確かめたことがあれば、同じ節の最後の `> **理由**` の枠に書く（本文を言い直すだけなら、枠は作らない）。人の名前（「Roze が選んだ」「Claude のおすすめだった」など）は書かず、理由の中身だけを書く（AGENTS.md の決まり 10）。前の決定を変えたときは、本文を新しい決定に書き換え、理由の枠の「採らなかった案」に前の決定を残す |
| 言葉の意味 | 用語集 `docs/glossary.ja.md`（言葉を決めた理由は書かない） |
| 新しく出た問い | 宿題一覧に足し、木にもぶら下げる |
| 進み | 作業メモ（save-notes スキル）：決まったこと、Roze の大事な言葉、木の更新 |

- 設計書には、決まったことだけを書く（本文に「決めること」や「案」は書かない。突き合わせが警告する）。仮決めは「仮決め」と書く
- 書いたら `python scripts/doc_check.py` でエラー 0 を確かめる
- コミットはしない。区切りで commit スキルを使う（Roze の OK のあと）

## ⑤ 具体例で試す

決まったことを、今までの決定と組み合わせた具体例で試す。

- ほころび（どこにも扱いが書いていない、2 つの決定が食い違う）が見つかったら、新しい問いとして木と宿題一覧に足す
  - 例：「発火中に届いた同じパスの変化は待たせる」×「来てすぐ消えたファイルは作成と削除の 2 つ」→ 削除のトリガーは、作成の発火が終わってから走るか
- ほころびが無ければ、そのまま次の回へ。見せる価値のある例は、次の回の問いの具体例に使う

## ⑥ 終わり方

- 聞ける問いが無くなったら（範囲の木がすべて決まったら）
  - 決まったことを、図 1 枚と箇条書きでまとめて見せる
  - 「これで分かり合えたか」「黙って前提にしていることは無いか」を Roze に確かめる。Roze が「はい」と言うまで、終わりにしない
- 途中でやめるときも、木と進みを作業メモに書いてから終える（次の会話で、木の続きから始められるように）
- 終わったら、doc-check（前回からの差分）と commit をすすめる

## 木の書き方

作業メモの「まだやっていないこと」に、次の形で書く。

```markdown
- 決めることの木（/grill。下は上が決まってから聞く。→ は今聞ける。範囲：論理設計の動き方）
  - → ランの結果の種類（宿題一覧 7）
    - 無視と溢れを、どのログに残すか（宿題一覧 7）
      - ログの列に、無視の理由をどう書くか（宿題一覧 7）
  - → 時間の上限（宿題一覧 6）
```

- 決まったものは、木から消す（日付の記録に「決まった」と書く）
- 仮決めは木に残し、「仮決め」と書く
