# 文書の突き合わせ

文書どうしのずれを、**機械**（スクリプト）と**目**（エージェント 2 人）の 2 段で調べ、Claude 自身が確かめてから Roze に報告する。

```
① スクリプト ─→ ② エージェント 2 人（並行）─→ ③ 報告を保存 ─→ ④ Claude が裏を取る ─→ ⑤ Roze に報告
  機械で分かるずれ    意味のずれ・抜け           あとから読めるように    誤検知を捨てる         直してよいもの／判断が要るもの
```

## ① スクリプトを走らせる

```bash
python scripts/doc_check.py --todo
```

- **エラー**：リンク切れ、無い論点への参照、閉じていないコードブロック、用語集の並び順の決まり違反（定義に、下で定義する言葉を使っている）
- **警告**：使わない言葉のうち機械で分かるもの（単独の「イベント」、「ルール」）
- **お知らせ**：決定していない論点、「残り」のある論点、英訳とのずれ
- **宿題**：宿題一覧（`docs/todo.ja.md`）の「決めること」の一覧

## ② エージェントに読ませる（2 人を同時に）

Agent ツールで、次の 2 つを**1 つのメッセージで並行に**起動する。どちらも読むだけで、ファイルは変えない。

| エージェント | 見るもの |
|---|---|
| `term-guardian` | 言葉の使い方（定義どおりか、使わない言葉、層ごとの動詞、未定義の言葉を用語のように使っていないか） |
| `design-verifier` | 文書どうしの矛盾・反映漏れ・抜け（決定が用語集や設計書に書かれているか、「残り」が宿題に載っているか、考え漏れのケース） |

### 調べる範囲

| 範囲 | いつ |
|---|---|
| **変えた所だけ（既定）** | ふだん。前回の突き合わせからの差分だけを調べさせる |
| 全部 | 設計の区切り（章を書き終えた、論点を用語集に反映した）、Roze に「全部」と頼まれたとき、前回の記録が無いとき |

- 全部を読ませると、1 人あたり約 17 万トークン・約 10 分かかった（2026-10-19 の 1 回目）。ふだんは変えた所だけにして、軽くする
- 前回のコミットは、`.claude/state/doc-check/` のいちばん新しい記録の先頭に書いてある（③）。差分は次で出す（まだコミットしていない変更も入る）

```bash
ls .claude/state/doc-check/
git diff <前回のコミット> -- docs/
```

### 頼むときに渡すもの

- 調べる範囲
  - 変えた所だけなら、上の差分そのもの。「差分の行を中心に調べ、照らし合わせに要る所だけ、ほかの文書を読む」と書き添える
  - 全部なら、「全部」と書く
- ① の結果（同じことを二度報告させないため）
- 「指摘には、ファイル名:行番号と、根拠になる文の引用を必ず付ける」

## ③ 報告を保存する

2 人の報告が届いたら、④ の前に、**そのまま**ファイルに保存する。

- なぜ：報告は、その会話の中にしか残らない。会話が要約されたり、別の会話から続きをしたりすると、指摘の全文が読めなくなる（1 回目は、別の会話の記録を掘り返して取り出すことになった）
- 置き場所：`.claude/state/doc-check/`（git には入れない。`.gitignore` 済み）
- ファイル名：`YYYY-MM-DD-HHMM-term-guardian.md`、`YYYY-MM-DD-HHMM-design-verifier.md`
- 先頭に次の 3 行を足してから、報告を丸ごと貼る

```markdown
- 日時：2026-10-19 16:00
- コミット：27013ba（`git rev-parse --short HEAD`。まだコミットしていない文書の変更があれば「＋未コミットの変更」）
- 範囲：変えた所（git diff 9a49b5f -- docs/）／全部
```

- ⑤ で報告したら、作業メモにこのファイル名を残す（save-notes スキル）

## ④ 裏を取る

エージェントの指摘は**そのまま信じない**。指摘ごとに、引用された行を自分で読んで確かめる。

- 引用が本当にそこにあるか
- 用語集・議論の記録の決定と、本当に食い違うか（文脈を読むと問題ないことがある）
- 確かめられなかったものは捨てるか、「未確認」と書く

## ⑤ Roze に報告する

次の 3 つに分けて、箇条書きで出す。各項目に `ファイル:行` を付ける。

1. **すぐ直せる書き間違い**：リンク、記号、言い回し、反映漏れのうち決定済みの内容を写すだけのもの
2. **Roze の判断が要るもの**：用語集の定義を変える必要があるもの、2 つの決定が食い違うもの、新しい言葉が要るもの、考え漏れ。→ 論点を立てる候補として出す
3. **宿題の数**：宿題一覧の「決めること」の件数と、増えた・減ったもの（全部は並べない。求められたら出す）

### 判断が要るものの聞き方

Roze は図と具体例で考える。抽象的な聞き方では伝わらない（1 回目：「依存先が移動したあとのジョブは？」「発火中に届いた変化は？」が伝わらず、聞き直した）。

- AskUserQuestion で、1 回に 4 問まで。大事な順に聞く
- 1 問ごとに、本文か preview に次を書く
  - **具体例**：ファイル名・ジョブ名・トリガーの中身・時刻を入れた時系列。コードブロックの図にする
  - **用語の意味をひとこと**：その問いに出てくる言葉（例：「依存先」＝ B に「A が成功してから始める」と書いたときの A）
  - **なぜそう設定するのか**：利用者がその設定をする理由（例：警告を消すために依存を足した）
  - **選んだら何が変わるか**：選択肢ごとに、上の例がどうなるか
- おすすめを先頭に置き、ラベルに「（おすすめ）」と付ける
- Roze が「分からない」「そもそも起きないのでは？」と答えたら、言い直すより、例をもっと具体的にする（起きる場面を 2〜3 個並べる）

悪い聞き方：

> 依存先が移動したあとのジョブは、無視でよいですか？

よい聞き方（2026-10-19 に聞き直したときの形。このあと Roze が決めて、B は走ることになった）：

```
トリガー T：inbox・作成・*.pdf
  ジョブ A：report.pdf を done\ へ移動する
  ジョブ B：Slack に「届いた」と知らせる（B は A に依存。A の移動の警告を消すため）

A が成功 → B は始める直前に C:\inbox\report.pdf を確かめる → もう無い → B は無視
```

> A が成功したとき、B を走らせますか？

### 直すときの決まり

- 1 は、Roze が「直して」と言ったら直す。直したら ① をもう一度走らせ、エラー 0 を確かめる（ここがループ）
- 2 は直さない。**用語集の中身は、議論の記録に論点を立て、Roze が決めてから**変える
- 直したら、save-notes スキルで作業メモに残す
