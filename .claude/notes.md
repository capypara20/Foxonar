### アプリの形（方針案。まだ決定ではない）
- Roze の考え
  - 常駐アプリ兼 GUI アプリ。常駐は OS のサービスでもよい。あくまで利用者が設定したとおりに動くもの
  - 画面は、設定と履歴を見るためのもの
  - Web のほうが豊かにできそう。ただし Web サーバを抱えるので、セキュリティが心配
  - ログファイルは、その時にならないと読まない → OS の通知に投げたい。どれくらい貯めるかも考える
  - 設定ファイルは手で書くより、画面から書き込む形がよさそう
- 確認した答え
  - Linux：画面のないサーバーでも使いたい
  - ほかの PC・スマホから見る：いつかは欲しい
  - 起動：ログイン時とサービスの両方を選べるように
  - 画面に使う言語：こだわらない
- 方針案
  - コアと画面を分ける。コアは画面なしで動く
  - 画面は Web を基本にする（画面のない Linux では egui が動かないため）。コアに Web サーバを内蔵する
    - 既定は、その PC からだけ（127.0.0.1）＋合言葉（トークン）必須
    - 画面のないサーバーは、SSH のトンネル（`ssh -L`）で手元のブラウザから見る
    - ほかの PC・スマホはあとで。そのとき HTTPS と認証を設計する
  - 設定は画面から書く。書き手はコアだけ（画面 → API → コアが確かめて書く → 読み直す）
    - ファイルは人が読める形のまま残す（画面のないサーバーでの緊急の手直し、バックアップ、git 用）
    - 一時ファイルに書いてから名前を変える。読み込みに失敗したら、前の設定のまま動き続ける
  - 通知（用語集の notice）の受け取り手：検知ログ、ランログ（どちらも Web UI で見る）、デスクトップ通知（何を知らせるかは利用者が選ぶ）。下の「言葉の整理」
  - 起動の注意：Windows のサービスはセッション 0 で動くので、画面も OS の通知も出せない。権限が強い（LocalSystem）。ネットワークドライブが見えない
    - サービスでも「動かすユーザー」を選べるようにする（Roze 賛成）
    - 案：サービスのときの OS の通知は、ログイン中のユーザー側の小さな常駐役（トレイ）から出す
- 新しく出てきた言葉：コア、Web UI、CLI、検知ログ、ランログ、デスクトップ通知。決まりどおり、論点を立ててから用語集に足す（下の「言葉の整理」）
- 画面の作り方（素の HTML＋JS、htmx、Rust で書く Leptos / Dioxus、egui の WASM など）は設計書で決める
- `Cargo.toml` の eframe（ネイティブ GUI）は、この方針だと要らなくなるかもしれない。決まってから外す
- お手本：Syncthing（常駐＋localhost の Web 画面＋API キー）

    - ジョブの一覧は設定ファイルの中にもともとある（トリガーや依存がジョブを指すため）
    - 未定：トリガーの名前も残すか

  - Rust の `tracing` の span を使うと、ランの中で出した記録に自動でラン ID が付く
  - 注意：2 つのログの保存期間がずれると、片方からもう片方をたどれなくなる
